# ShipTok Guide For AI Contributors

This repository is ShipTok, Revyl's iOS app (SwiftUI, iOS 17+). People sign in with Revyl using their GitHub account, and that sign-in and each person's settings run on Revyl's backend, under its ShipTok API (`/api/v1/shiptok/`), which lives outside this repository. ShipTok is a vertical feed of the pull requests that carry media in the repository the person chooses, one pull request per swipe with its ShipTok video or other media first: open ones in Open mode, merged ones in Merged mode, and one card per weekly edition in Weekly mode, whose media can be a video, image or GIF. Likes, reactions, comments and vibes are GitHub reactions and comments written as the signed-in person, so GitHub is the record.

---

# Guidance & Rules

The rules below are binding for the whole repository.

## Ownership And Boundaries

- **[STRICT]** The app reads and writes GitHub directly with the signed-in person's GitHub token, never through Revyl's backend. Besides GitHub, only the build's Revyl backend ever receives the token: with settings and deletion requests, and with a request for a video it hosts, so it can check GitHub lets the person read the video's private repository, while playback follows the redirect to the file without it (Signed Media URLs). The app reads no Revyl product database directly.
- **[STRICT]** GitHub is the record for pull requests, weekly videos, media, comments, reactions and vibes. The viewer's changes to one reaction on one pull request, week or comment reach GitHub in the order they were tapped, and only the newest one failing undoes what the app shows. Revyl's backend holds only what GitHub can't: it redeems and refreshes the GitHub sign-in with Revyl's GitHub App, since both need the App's client secret, and keeps each person's settings keyed by their numeric GitHub user ID, which it reads from the GitHub token on every settings request. It stores no GitHub token and never proxies a GitHub write or a person's read; its one GitHub read for the app is whether, before a hosted video from a private repository plays, the person's token can read that repository (Signed Media URLs). Its ShipTok tables link to no Revyl user or organization.
- **[STRICT]** Sign in with Revyl is the app's only sign-in, and the app keeps no other provider's session or a reader for one. Its identity is the person's GitHub account through Revyl's GitHub App, so it needs no Revyl account or seat.
- **[STRICT]** Delete my ShipTok data removes everything ShipTok keeps for the person: Revyl's backend deletes their settings and revokes the GitHub token the app presents, and the app then deletes its Keychain sign-in, caches and defaults and signs out. Sign out never signs out while the Keychain still holds the sign-in, and Delete my ShipTok data reports success only once the Keychain lets the sign-in go and the app's own caches (its saved feeds, saved media and URL cache) and defaults are gone too; anything else iOS keeps under Caches is swept best effort. Once Revyl's part is done the app records that in its defaults, by GitHub user ID, until the iPhone's part finishes, and never shows the revoked sign-in again: if the iPhone's part fails, then or on a launch, the app stays on the sign-in screen saying the deletion is unfinished, and the next launch or sign-in, before it opens GitHub, finishes only the iPhone's part. It revokes only that token, never the person's whole authorization of the GitHub App, which would also sign them out of every other Revyl surface on the same App. Comments, reactions and vibes are GitHub's record and stay there. Anything new the backend or app keeps per person joins this deletion in the same change.
- **[STRICT]** The ShipTok format is a contract shared with Revyl's pull request review config and the people who post ShipTok videos: which pull requests are in the feed, the ShipTok video marker and tag, which media shows first, the vibe comment, and the weekly edition issue. It is documented in `docs/shiptok-format.md`. Change the parser or the vibe comment only together with that contract, and read the hidden `<!-- shiptok:... -->` markers from the raw markdown body, since GitHub's rendered HTML drops them.
- **[STRICT]** Only top-level conversation comments by people, on a pull request or a week's issue, show as comments. Bot comments, inline code-review comments and comments carrying a ShipTok tag never do, whether or not they hold a video, while media from any top-level comment, a bot's included, counts.
- **[STRICT]** A ShipTok video is a video in a description or top-level comment tagged with case-insensitive `#shiptok` or `<!-- shiptok:video -->`. Attributes in the hidden marker are ignored; authorship and hosting provider never change the tag's meaning. The newest tagged video plays first, ahead of other media. People make videos with their own tools; the app does not require or infer Revyl generation.

## Report And Hide

- **[STRICT]** Everything people post that ShipTok shows can be reported and its poster hidden, as App Store guideline 1.2 requires of an app that shows user-generated content. Report opens GitHub's own report form for that pull request, week's issue or comment, since GitHub hosts the content and acts on reports; ShipTok sends and keeps no report of its own. GitHub's form takes no reaction, so someone shown only for a reaction can be hidden but not reported. Hide takes everything the person wrote or posted (their pull requests, weeks, comments, vibes and media) out of the feed, decks, comment sheets, detail sheet and inbox for the signed-in person. It filters what is shown, never what is saved or fetched, so Unhide brings everything back at once.
- **[STRICT]** Hidden people are kept by GitHub login, only on the device and per signed-in person. Settings lists them with Unhide, and deleting ShipTok data clears them. A new surface that shows what people post honors the hidden list and offers Report and Hide in the same change.

## iOS App

- **[STRICT]** `scripts/revyl/remote-build.sh` (`setup` / `compile` / `zip` / `upload-to-testflight`) is the only build pipeline; never fork a second one.
- **[STRICT]** ShipTok belongs to Revyl's Apple team, Revyl, Inc (`9MQ4RWNL3N`), and to no other: the project's `DEVELOPMENT_TEAM` and `upload-to-testflight` both name it. Its bundle id `ai.revyl.shiptok` is the app's only one; extensions and app groups use `ai.revyl.shiptok.<suffix>`.
- **[STRICT]** `upload-to-testflight` takes the team's App Store Connect API key from its environment at run time and keeps it only in a temporary file it deletes; the key itself never enters the repository. It archives unsigned and lets the export sign with Revyl's cloud-managed distribution certificate, so never add a signing identity, certificate or another team's key to a machine or the repository for it.
- **[STRICT]** The Xcode project uses a synchronized folder: files under `ShipTok/` join the target automatically, so do not add per-file entries to `project.pbxproj`.
- **[STRICT]** The app holds only public configuration: the Revyl backend URL its build names and PostHog's project ingestion key. Every build uses Revyl's production backend unless the `SHIPTOK_REVYL_BACKEND_URL` build setting names another, for example a development backend with its own GitHub App. The GitHub App client secret, PostHog personal keys and database credentials never enter the app or git.
- **[STRICT]** GitHub access and refresh tokens, signed media URLs and tokened Revyl media URLs are credentials. Never log, render, copy or persist them outside the Keychain.
- **[STRICT]** GitHub sign-in runs in an ephemeral browser session. A shared session first shows iOS's "wants to use … to sign in" prompt, and on an unfolded iPhone Duo continuing from that prompt tears the GitHub sheet down before it appears, so sign-in silently does nothing there.
- **[STRICT]** A sign-in lasts until GitHub refuses to refresh it. A GitHub App user access token expires after eight hours and its refresh token works once, so the app refreshes ahead of expiry, and once when GitHub or Revyl refuses a token another refresh may have retired, one refresh at a time, saving the rotated pair to the Keychain before anyone uses it. A pair the Keychain fails to save stays in memory and is saved again before use, never refreshed anew, since its refresh token is the only one GitHub still honors. An App that doesn't expire its tokens keeps one until GitHub rejects it. A refusal ends only the sign-in whose request it answered, never a later one, a hosted video's refusal ends none (Signed Media URLs), and nobody can sign out while Delete my ShipTok data runs.
- **[STRICT]** `ShipTok/PrivacyInfo.xcprivacy` declares the data the app sends off the phone and its required-reason API uses, and the ShipTok section of Revyl's privacy policy (https://revyl.com/privacy/#shiptok) describes that data to people. A change that sends a new kind of data to Revyl, PostHog or GitHub updates both in the same change, and one that uses another required-reason API, even on data that never leaves the phone, updates the manifest.
- **[STRICT]** A test phone signs in to GitHub only as `revyl-shiptok-tests`, the GitHub account that exists for ShipTok's tests, never as a person, so nothing a test does is posted or signed in as someone's own account (Revyl).
- **[STRICT]** The feed's repository is the person's choice among every repository their sign-in reaches, meaning where an organization installed the build's GitHub App and the person has access, with no other allowlist; Debug and Release share one picker. The choice is remembered per person, and with none the app opens RevylAI/shiptok-demo, Revyl's public example repository, when it's reachable, else the picker. A repository the App stops reaching sends the person back to the picker, not to sign-in. Each API client keeps its repository fixed, and changing the choice rebuilds the feed, weekly and inbox state; saved feeds and inbox read positions are scoped by repository and person.

## Product Analytics

- **[STRICT]** Capture native product facts through the typed boundary in `ShipTok/Analytics/`, whose typed events are the event contract. Keep delivery independent of product success, and record GitHub write success only after GitHub confirms it.
- **[STRICT]** Use the numeric GitHub user ID saved with the sign-in for analytics identity. Until GitHub names the person, a sign-in attempt's events use the attempt's own ID, which its completion carries. A login is renameable, and a repository owner is not a Revyl person or organization mapping. Events never let PostHog derive a location. Debug and Release use the web app's PostHog project, separated by `environment=development` and `environment=production` respectively.
- **[STRICT]** A watch starts only while a visible, foreground video is actually playing, never on mount, preload or download. Accumulate only playing time, exclude pauses, buffering, scrubbing and comment-sheet occlusion, and summarize on leaving the video instead of emitting frame or loop events. Analytics visibility must not change playback behavior. Report terminal playback failures only after the existing media-renewal path is exhausted, not an expected first URL expiry. Do not send media URLs or media IDs, tokens, titles, comments, feedback text or other content. Subject and source-comment IDs are correlation keys, not breakdown dimensions. No repository name, and nothing that identifies a person the viewer reports or hides, enters analytics.

## Card Layout

- **[STRICT]** Every screen follows Instagram Reels, and the feed page's layout reads only the window's size, its safe area and the regions the system reports as covering it, never the device model or orientation (`ShipTok/Feed/FeedPageLayout.swift`). Where a card at least as wide as a 9:16 video of its height fits centered between two 84-point columns (wider when the system's trailing strip is), as on the unfolded iPhone Duo held tall, the card has small rounded corners and runs from at most 30 points below the top of the screen to 30 points above a floating pill tab bar, with the action rail in the right column. Anywhere else no tab bar shows, so the video keeps the screen's height: the card runs from the window's top edge to its bottom edge, under the status bar and home indicator, either beside a trailing system strip of at least 56 points that holds the rail, as on the folded Duo, or across the whole window with the rail over its trailing edge, as on other iPhones. The caption, rail, progress line and scrub strip stay above the home indicator.
- **[STRICT]** The tab bar holds the feed, the inbox and settings, shown as the viewer's avatar. Without it, the feed itself is home, and the inbox (a tray with the unseen count) and settings (a gear) are plain glyphs, drawn and spaced like the rail's at the top of the status strip, below every region the system reports there, or at the right end of the top row, the last centered 23 points from the card's edge. The inbox and settings replace the feed while its video is paused, and without a tab bar their navigation bar leads back with "‹ Feed".
- **[STRICT]** Over a card that fills the window, the top row sits 8 points below the safe area, never higher than 32 points from the top of the window. Over an inset card, which already starts under the status bar, it sits 32 points from the top even where the Duo's status capsule covers the card's corner, as Reels' own row does. The row holds the Open / Merged / Weekly tabs, plain bold text with the selected one white and the others dimmed; while a week's pull requests are open, a plain chevron and the week's dates take their place and lead back to the weeks. Both keep to the row's free stretch: the widest part of the row at least 8 points clear of its inbox and settings glyphs and of every region the system reports over it, such as the Duo's status capsule. The rail starts below the row or sits beside the card, and the status strip lies beside the card, so nothing in the row ever overlaps them. One rule places the tabs on every window: they center on the card when they fit in the free stretch there, otherwise they move toward its free side only as far as it takes to stay in it, and when they're wider than the whole stretch they shrink evenly to its width, down to half their size. The way back sits at the free stretch's leading end. The "new" pill (Feed Order) sits centered over the card, 8 points below the row.
- **[STRICT]** The rail holds plain glyphs with their counts: like (a long press opens every reaction), comments, react, mute and playback speed for a video that loads, and the deck: on a pull request when it has more than one item or its hero is a still or GIF, and always on a week, where it opens the week's pull requests; and last, More, whenever the card shows something someone else posted (Report And Hide). The speed, also among the deck's controls, cycles 1x, 1.5x and 2x for every video and is remembered on the device. The rail starts below the strip's buttons, or below the top row when it sits over the card, and below every region the system reports as covering its column, such as the Duo's status strip with an expanded island or Live Activity, and its gaps shrink to fit what's left, down to overlapping the padding around its glyphs. The caption sits over the card's lower left above a thin video progress line, light grey where it has played over an opaque dark grey track, which spans the card 2 points above the home indicator when the card fills the window and otherwise runs 3 points in from the card's sides, 9 points above its bottom.
- **[STRICT]** The hero never loses more of itself than the card's shape forces. A shape that loses at most an eighth of itself when filling the card crops to fill it, as a 9:16 video does on the folded Duo and the unfolded Duo held tall. Any other shape, a 9:16 video on another iPhone's taller screen and a wide screenshot or GIF included, shows whole over a blurred copy of itself, centered between the top row and the home indicator or the card's bottom, so there are never black bars, no part of a screenshot is cut off and no edge of the media runs through the top row.
- **[STRICT]** Text on a card stays short, one line each: the author with the viewer's own vibe badge, the title, and the number with when it merged ("merged 2 days ago") or, on an open pull request, when it was last updated ("updated 2 hours ago", led by "Draft · " on a draft). A week shows its "ShipTok weekly" chip and dates, title and hook instead, its title on up to two lines, since a week has no detail sheet and its caption opens its pull requests. Everything else (the full title, the description, stats, labels, everyone's vibe and reaction counts) is one tap away in the detail sheet, which says when the pull request merged, or that it's open or a draft and when it was last updated, and the swipe legend lives in Settings.
- **[STRICT]** The caption sits on a backdrop that keeps it legible on any media: a blur under a black tint that reaches 0.65 at the caption's top line and holds it down to the card's bottom, so on pure white media the caption keeps at least 4.7:1. Above the caption the backdrop fades in over at most 80 points and never starts above 1376/1920 of a 9:16 ShipTok video laid out on the card as the hero lays it out, the bottom of the band where a ShipTok video keeps everything a viewer must read, so the video's own captions stay sharp on every window. Where the caption itself reaches above that line, the backdrop starts at the caption's top. Over a video the blur clears just above the progress line, and the hero draws the line over the backdrop, so the tint never darkens it and the line stays sharp.

## Feed Order

- **[STRICT]** Open and Merged each hold the chosen repository's pull requests that carry media (`docs/shiptok-format.md`), at any age, with no time window, label or grouping: Open the open ones, drafts included, newest update first; Merged the merged ones, newest merge first; ties go to the higher number. A pull request closed without merging is in neither. Each mode reads its newest page first and keeps reading older pages as the viewer scrolls, until the repository has no more.
- **[STRICT]** Open reads the repository's open pull requests 25 at a time through its pull request list, ordered by update, never through search, and holds every one once the list has no next page. Merged reads merge-date windows going back from its cursor, the whole second where the window it last read begins, or from when its first page loads. One request counts the merged pull requests in spans ending there (6 hours, a day, 3 days, a week, 2 weeks, 30 days, 90 days, a year, and everything older), and the window is the widest span holding at most 50, or the 6-hour span when none does. The window is read whole through search, split at whole seconds into ranges read in parallel while a range holds more than 125, and a range one second long is paged whole, as far as the 1,000 results GitHub search gives one query, so Merged misses pull requests only if more than 1,000 merged in one second. Only a window read whole moves the cursor to its start, so a window another mode cut short moves nothing, and once the span with no start is read Merged holds every merged pull request and has no cursor.
- **[STRICT]** Older pull requests load once the viewer is 5 or fewer shown cards from a mode's end, its end page included, and page after page loads until 10 more cards show, nothing older is left or the mode leaves the screen. Both counts are of the cards the viewer is shown, after Hide and Videos only, while the analytics event for each older page records both how many pull requests it added and how many of those the viewer is shown. Each page is sorted and put below every loaded card, so nothing moves under the viewer; a card on it updated after the cards below it were read takes its slot like a newly found one, and a pull request already loaded updates in place. The viewer's card keeps its place as cards arrive or leave around it, and on the end page the viewer stays just past every card they had, so the first older card that loads is the one they see next.
- **[STRICT]** Videos only is a person's setting, on by default. While it's on, Open and Merged show only pull requests whose first media item, after hidden people's media goes, is a video; while it's off, ones whose first media is a screenshot or GIF show too. Weekly and a week's deck show every week and pull request either way. Like Hide, it filters what is shown, never what is read or saved, so turning it off brings cards back at once and turning it on near a mode's end loads more once the mode is on screen. The choice goes to Revyl's backend with the person's other settings as `shows_only_pull_requests_with_videos`, and saved settings without it read as on. The app shows the settings Revyl last confirmed with each setting's newest change still saving on top. A read of the settings updates only the confirmed ones and is dropped if a save succeeded while it ran. Saves run one at a time, each sending every setting as it stands when its turn comes, and a save settles its setting only if no newer change to that setting followed it, so a failed save shows the confirmed value again unless a newer change is still saving.
- **[STRICT]** An iOS app always shows the newest data it has, so while the feed is on screen, rather than Inbox or Settings, the mode it shows reads GitHub again when it shows, when the app returns to the foreground, 10 seconds after its last read finishes, and on a pull from its first card. Inbox and Settings, from the tab bar or the glyphs that stand in for it (Card Layout), take the mode or a week's deck off the screen: its reads, focus, older pages, the week's loading and media link renewals stop, what waited on the viewer settles (below), and coming back focuses the card the viewer is on and carries the week's loading on where it stopped. A refresh first reads the card in focus in full. Open then lists the repository's closed and merged pull requests updated since its last refresh, with 3 minutes of overlap, and they leave Open; it then lists the open ones updated since, with the same overlap. Merged lists the merged pull requests updated since its last refresh, with the same overlap, through the repository's pull request list ordered by update, never search, keeping those merged since its cursor, or any once it holds them all. Each mode reads in full by id, 25 at a time, the listed pull requests it hasn't already taken in at that update and merge date (Feed Caching), and applies each batch before reading the next, so a failed batch loses none read before it. A card coming into focus is read again, renewing its media links when they're more than 2 minutes old, and the next card the viewer is shown has its media links renewed once they are. Older pages, the reads around the card in focus and the read that renews a pull request's failed media link belong to what's on screen and stop when it leaves; a failure recorded while neither a mode nor a week's deck is on screen waits for the next read (Signed Media URLs).
- **[STRICT]** When GitHub throttles the signed-in account, the app asks GitHub nothing more, from any screen, until the time its `Retry-After` header gives, else until `X-RateLimit-Reset` when the hourly quota is used up, else for 60 seconds. A throttle is a 429, a 403 that says the quota is used up, carries `Retry-After` or names a secondary rate limit, or a GraphQL `RATE_LIMITED` error inside an answer GitHub sends as successful; an answer saying the quota is used up starts the same wait. Any other refusal is an ordinary failure.
- **[STRICT]** A pull request found after a mode opened, or one whose update changes its slot, takes its sorted slot. At or above the card in focus it's flagged for the "new" pill, which counts such cards and jumps to the first. Below, it never lands above or between the card in focus and the next card the viewer is shown, since both are already rendered, and waits just after them until the viewer moves to another page; cards the viewer isn't shown, hidden or filtered out by Videos only, don't count as that next card. Those two cards keep their slots when they change and move once the viewer moves on, and the card the viewer just left moves without the pill. One sorting below every loaded card waits for its own page unless it may go last: in Open once Open holds every open pull request or has none, in Merged when it merged at or after the cursor.
- **[STRICT]** A card that stops belonging to its mode leaves it: an open pull request that merges or closes, one GitHub no longer has open or merged, or one left with no media. The card under the viewer's finger stays until they move to another page or the mode leaves the screen, and so does the copy of it they see: a fresh read they wouldn't be shown, with no media left to show or, under Videos only, no video first, waits and takes its place once they move on, and a later read they can be shown cancels the wait. Hiding a person and changing Videos only still apply to that card at once, and being told the same page again changes nothing. When a mode leaves the screen, for another mode, a week's deck, Inbox or Settings, what waited on the viewer settles, a leaving card going, a waiting copy taking its card's place and held cards taking their slots, while the viewer's place stays, moving to the next card when its own leaves; off screen, a card that leaves goes at once.
- **[STRICT]** A pull request is dead for a viewer once every media item it holds, hidden people's included, is given up: refused to them, or failed again from a renewed URL (Signed Media URLs). One with no media left isn't dead; it leaves as above. One whose media the viewer can see is all given up while a hidden person's isn't is out of their sight instead, the way Hide leaves cards out: every mode and an open week's deck leave it out at once, the card under the viewer's finger included, and it's back once Unhide brings media that isn't given up into view. A dead pull request leaves every mode and an open week's deck as a card that stops belonging does: at once, except the card under the viewer's finger, which goes once they move off it. A card a mode or a week's deck opened on that the viewer hasn't moved off goes at once instead, so it lands on the next card the viewer is shown, or past its last card when none is left. A mode the viewer comes back to, from another mode or tab, counts as opening on the card it shows; a week's deck counts as opening only when the week opens. On a card the viewer has reached, and on a deck page, media given up says its video or image is unavailable; until then it keeps the loading look.

## Feed Caching

- **[STRICT]** Open and Merged are saved on the device for the repository and signed-in GitHub login when the app goes to the background, before the person picks another repository, and after older pull requests load. Each is saved with the moment every update before it was applied; Merged also with its cursor, or that it holds every merged pull request, and Open with GitHub's cursor for its next page, or that it holds every open one. Each card is saved as it will stand once the viewer moves on (Feed Order). A launch opens on the saved feeds at once, however old they are, keeping the cards that still belong to their mode in feed order, and each mode then refreshes from the moment every update before its saved feed was applied.
- **[STRICT]** Each mode records, for every pull request it takes in from a read or a page, the update and merge date it took, and its refresh doesn't read again a listed pull request it already took at both, so one read as open that merged in the same second is still read for Merged. The record lasts for the app session and isn't saved or rebuilt from the saved feeds, so the first refresh after a launch reads in full every pull request its lists keep, among them any from the 3-minute overlap that still qualifies for the mode, even one the saved feed already holds at that update. Some reads always happen: the card in focus is read in full on every refresh and whenever it comes into focus, the next card the viewer is shown is read again when its media links are due for renewal, and Weekly and an open week read GitHub afresh each time. Comments, reactions and vibes stay live through the card in focus.
- **[STRICT]** The saved feeds carry a format version, now 8. Reading them decodes every saved file and deletes each one that doesn't decode or holds another version, whoever's it is, so a change to what's saved, or to a check below that decides it, moves the version. Feeds saved before Open existed sit in a folder of their own, which every launch deletes in the background and Delete my ShipTok data removes with the app's other caches.
- **[STRICT]** A saved feed holds no signed media URL, tokened Revyl media URL, description, comment or rendered HTML. The free text it keeps, titles and label names, is redacted when the pull request is read, as on every surface that shows it (Signed Media URLs). A saved media item keeps its URL only when it isn't a credential, so its media plays from the device or waits for the refetch of the card in focus. A tokened Revyl media item's id is a hash of its canonical URL, never the token or the redirect target. Open's next page is saved as GitHub's list cursor, which holds no credential.
- **[STRICT]** The feed's reads and saves belong to one sign-in. Sign out and Delete my ShipTok data stop them and wait for what's running before going on, and a save the ended sign-in cancelled writes nothing, so nothing read for a sign-in is saved after it ends.
- **[STRICT]** Media is kept per viewer, since a private repository's media is only for people who can read it: a sign-in's loaded images and videos, failed loads and downloads are its own, its saved files sit in a folder named for the person's GitHub user ID. A load takes its viewer's media cache before it awaits anything and keeps what it gets only there, so no viewer ever reads another's media, however late a cleanup lands or if it fails. Saved files are named by a hash of their media item's id and play from the device on later launches. The modes, weeks and decks share their viewer's files, so a file goes once it has gone 30 days without being saved or shown, never by one surface's list. When a sign-in ends (Sign out, GitHub refusing its refresh, or Delete my ShipTok data) its downloads stop unsaved and its loaded media and folder go as cleanup, and Delete my ShipTok data removes every viewer's saved media.

## Weekly Mode

- **[STRICT]** The feed has three modes, Open, Merged and Weekly, chosen with the tabs at the top of the feed (Card Layout). It opens on Merged the first time and then on the mode the person last chose, remembered on the device; a stored mode it doesn't know opens Merged. Each mode, and a week whose pull requests are open, keeps its own place and its own loading, failure, end and empty pages.
- **[STRICT]** Weekly shows one card per closed issue in the chosen repository labeled `shiptok-weekly` whose description follows the weekly format in `docs/shiptok-format.md` and that carries media, newest week first, so two issues for one week are two cards. Its media can be untagged, and images and GIFs count: the card plays its newest tagged video, else its first video, else its first image or GIF. The app lists the closed issues with the label through the issues API, never search, 25 at a time, most recently created first, until none are left, then leaves out a description outside the format or an issue with no media and sorts the rest by week. A week shows on the first read after its issue closes, and the app never edits, reopens or closes an issue. Posting weeks is the poster's job, never the app's.
- **[STRICT]** Weekly's reads belong to the feed view, not to the mode reads above: while Weekly is on screen it reads the weeks when it shows, when the app returns to the foreground, 10 seconds after its last read finishes and on a pull from its first card, and a week coming into focus more than 2 minutes after the last read reads them again, as does a weekly card's failed media load, to renew its links, even with Inbox or Settings over the feed, unless the failure gives the item up at once (Signed Media URLs). The repeating reads stop when Weekly leaves the screen, and a read a pull, a week coming into focus or a failed media load started runs to its end. A weekly card whose media is given up stays and says its video or image is unavailable; only pull request cards leave for dead media (Feed Order).
- **[STRICT]** A week takes likes, reactions, comments and vibes on its issue exactly as a pull request does. Its deck opens the week's pull requests as ordinary pull request cards in the video's order, each with its own likes, reactions, comments and vibes, and shows each one whatever Videos only says, less what hidden people posted. They're read by number, since a week can name pull requests neither mode has loaded, 6 at a time, each joining the deck once every one before it is in, so a page never moves under the viewer. The deck reads them only while it's on screen: leaving it, for another mode, Inbox or Settings, stops the reading and releases the deck's focus, letting a card waiting on the viewer go, and coming back carries on from the first pull request not yet in, at the viewer's place. One with no media, one dead for this viewer (Feed Order) or one closed without merging is left out. One whose read fails shows the copy a mode will hold once the viewer moves on, if a mode has one and it isn't dead for this viewer.
- **[STRICT]** The deck's focus follows the card on the viewer's page: the first card to arrive takes it, the next card takes it when the one under the viewer leaves, and the end page focuses none. While a week's pull requests are open, the card in focus is read again when it comes into focus and 10 seconds after its last read finishes, the next card's media links are renewed when due, and a pull reads the first card the viewer is shown. A week's card leaves the deck when a read finds it closed or with no media, the card in focus once the viewer moves on, a dead card leaves as Feed Order says, and the viewer's card keeps its place as cards leave around it. The card in focus keeps its media links, so a playing video isn't reloaded, unless they're more than 2 minutes old or failed to load.

## Signed Media URLs

- **[STRICT]** GitHub upload URLs come from its rendered HTML, signed for the reader, and stop working a few minutes after the fetch. A Revyl-hosted video's canonical source is the video target in the raw description or comment, including when a poster links to it; the poster is not another deck item. A media item's identity never includes the URL's query string, a video downloads once in a single request, never past the size limit in `docs/shiptok-format.md`, and every replay, loops included, plays from memory, and a fresh URL is fetched only after a load fails: a URL signed in its query string is renewed by refetching the pull request, and an unsigned one, such as a hosted video's tokened link that redirects to the file, by requesting it once more. A failed item is given up only once its renewed URL fails too, or a read that started after the failure brings back the URL that failed, and a failure no such read has settled yet waits for the next one, so a renewal that fails offline is settled once the app reads again. A hosted link is one whose path ends in the hosted video route and an upload's canonical name (`docs/shiptok-format.md`), under whatever path its backend is served from, and extraction recognizes it through the one check that says so. Media ids and saved feeds are broader on purpose: any link whose path holds the hosted video route, however it's escaped or cased, is a credential. Redaction never depends on reading a link: after keeping the labels of the links it can read, it removes from the text every run without spaces, quotes or brackets that holds the hosted video route followed by a token-shaped segment, relative or absolute, escaped, cased or bare, and keeps the prose punctuation (`.`, `,`, `;`, `:`, `!` or `?`) that trails it. A change to either check that could leave saved feeds holding a credential or a stale id changes their format version. A hosted video on a private repository plays only for a viewer Revyl's backend sees GitHub lets read it, so a signed-in person's request for a hosted link carries their GitHub token as a bearer token, only when the link's scheme, host and port are the build's Revyl backend and its path reads exactly as that backend's hosted video route and the upload, with no userinfo, escapes or dot segments; a link naming any other host sends none. A signed-in request never goes without the token: one that can't be had, offline while it renews for example, leaves the video loading rather than failed, and it is tried again a few seconds later, only while its card or deck page is the one being watched, in the foreground with nothing over it. GitHub refusing the sign-in, with no refresh token left or a refresh it turns down, and the sign-in ending are final for that viewer, so the video is refused to them at once without the video ending the sign-in. When Revyl answers with 401 to a request that carried the token, the sign-in is renewed the usual way, one refresh at a time, and the video requested once more. Any other 401, 403 or 404 the hosted route answers itself, never one from where a redirect leads, is Revyl's answer for this viewer. A video refused to the viewer is given up at once, with no renewed request or read, is never taken for an expired URL, and never ends the sign-in. Video redirects carry no GitHub authorization, since the file's link is signed in its query string and the token never leaves Revyl, so a 401 after a redirect never renews the token, and they never replace the canonical cache identity.

## Vibes

- **[STRICT]** A person has one vibe per pull request or week: a new vibe comment replaces their earlier vibe comments on it, and undoing it, from the toast or later from their own vibe badge, deletes it.
- **[STRICT]** Vibes have no button: a sideways swipe casts them, and VoiceOver offers Good vibes and Bad vibes as actions on every element of the card, which leave the way the swipe does.
- **[STRICT]** The vibe feedback box never blocks the swipe. The feed advances at once, the box is a per-person setting (on for bad vibes and off for good vibes by default), and feedback typed or spoken before the next swipe posts with its vibe.

## Swipe Gestures

- **[STRICT]** Swipe directions are a product decision: up shows the next card, down the previous one, right casts good vibes, left casts bad vibes, and a double-tap likes. A single tap on a playing video pauses it, showing a play glyph, and another tap resumes it; it waits out a double-tap, so a like never pauses, and the rail and caption keep their own taps. Change them only in the feed's swipe gesture mapping (`FeedSwipeGestureMapping`); the card stamp, settings, deck and the card's VoiceOver vibe actions read that mapping. Swapping directions within an axis is safe, while moving navigation to the horizontal axis needs deck layout changes.
- **[STRICT]** Holding a playing video past a tap's length plays it at 2x, with a "2x" hint, until the finger lifts and it returns to the chosen speed, and a sideways drag that starts on the strip around a hero's progress line, or on a deck page's line, scrubs it with a time readout, so neither costs a tap, double-tap, swipe or vibe, and neither reaches the tab bar or home indicator. The hold is UIKit's long press, since a SwiftUI long press on the video stops a single tap from pausing it, so it needs iOS 18; earlier systems keep the scrub.

## Revyl

- **[STRICT]** `.revyl/config.yaml` on `main` is the Revyl project's configuration. Revyl's GitHub App applies it on every push to `main` and refuses dashboard and `revyl config push` edits, so change it only in git and run `revyl config validate` before committing it.
- **[STRICT]** `.revyl/tests/` holds one Revyl test per journey through the app and `.revyl/modules/` the steps they share, and runs read them from git (`run_test_definitions_from_git`), a pull request's runs at its head commit. A change to a journey updates its test in the same change, and a new journey gets a new test, added to the ShipTok journeys workflow that `.revyl/config.yaml` names. Push a new or changed test or module with `revyl test push --include-modules-and-scripts` before committing it, and commit the `_meta` it writes, since `_meta.remote_id` ties the file to its test in Revyl.
- **[STRICT]** Every journey first signs in through `.revyl/modules/shiptok-sign-in-as-test-account.yaml` as `revyl-shiptok-tests` and opens RevylAI/kyle-expo, whose pull requests with media are the journeys' fixtures. The account's username, password and two-factor secret are Revyl global variables, never in git, and `.revyl/scripts/shiptok-github-totp-code.py` turns the secret into the current code, so every test that imports the module carries a secret `github-totp-code` test variable; `revyl test var set` can't mark one secret, so a new test gets it through Revyl's API.
- **[STRICT]** Sign-ins never overlap. GitHub accepts each two-factor code once, so two sign-ins in the same 30 seconds refuse each other: run journeys one at a time, or start each only after the one before it has signed in.
- **[STRICT]** A journey undoes every write it makes on GitHub before it ends (a like, reaction, comment or vibe), finds the card it wrote to by its pull request number, and never writes again to retry an undo. None submits GitHub's report form, signs out or deletes ShipTok data.
- **[STRICT]** Every build CI uploads carries its repository, head commit, branch and pull request, which Revyl's proof of changes and pull request workflows find it by; `revyl build upload` reads them from GitHub Actions, so keep uploads on it.
- **[STRICT]** `.agents/skills/`, linked for Claude Code from `.claude/skills/`, holds Revyl-managed skills from `revyl skill install`. Never edit them in place; when the Revyl CLI version pinned in `.github/actions/install-revyl-cli/action.yml` moves, refresh them with `revyl skill update` from that version.

## CI And Releases

- **[STRICT]** `.github/workflows/ci.yml` runs on every pull request and push to `main`: a gitleaks scan with `.gitleaks.toml`, then `scripts/revyl/remote-build.sh` (`setup`, `compile`, `zip`) on GitHub's `xcode-27` runner with Xcode 27.2, uploading the build to Revyl. On `main` it runs the ShipTok journeys workflow on that exact build and explores it with Atlas, one exploration at a time with every build queued. Fork pull requests get no secrets, so they build without uploading.
- **[STRICT]** `main` works against Revyl's production backend at every commit, and its journeys run on a build that uses production, so they show whether it does. An app change that needs new backend behavior merges to `main` only once that behavior is live in production, and waits on its own branch until then: one named after the cognisim-monorepo pull request it ships with, `cognisim-<number>-<what it does>` (for example `cognisim-6944-open-and-merged-pull-request-feeds`), pushed so it shows on GitHub, and never merged to `main` before that pull request is live in production. The app relies only on what production serves, and Revyl's backend only adds to the ShipTok API, so an app already on `main` or in TestFlight keeps working beside a newer backend.
- **[STRICT]** `.revyl/config.yaml` is the only place that names the Revyl app and workflows: CI reads them from it with `revyl config show --json`, and the repository's GitHub settings hold only secrets.
- **[STRICT]** `.github/workflows/release.yml`, run by hand with a build number, is the only way builds reach App Store Connect: it runs `upload-to-testflight` with the App Store Connect API key in the repository secrets `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_API_ISSUER_ID` and `APP_STORE_CONNECT_API_PRIVATE_KEY`.
- **[STRICT]** This repository is public, and so are its Actions logs: no workflow prints a secret, token, internal hostname or customer data.
- **[STRICT]** Workflows pin every action to a commit and the Revyl CLI and gitleaks to a release version.
