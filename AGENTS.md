# ShipTok Guide For AI Contributors

This repository is ShipTok, Revyl's iOS app (SwiftUI, iOS 17+). ShipTok is a vertical feed, one card per swipe, of what a GitHub repository posts with media: its open pull requests in Open mode and its merged ones in Merged mode, each led by its ShipTok video or other media, one card per weekly edition in Weekly mode, and one card per shipped feature in Features mode, where a week's or a feature's deck opens the pull requests behind it. A card's media can be a video, image or GIF. Nothing shows without a Revyl sign-in. A person signed in to Revyl connects their GitHub account and picks one of their team's repositories, and until they connect it, they look around a read-only demo of one public repository. Likes, reactions, comments and vibes are GitHub reactions and comments written as the person, so GitHub is the record. The Revyl sign-in, the GitHub connection, each person's settings, the demo and hosted videos run on Revyl's backend under its ShipTok API (`/api/v1/shiptok/`), which lives outside this repository.

---

# Guidance & Rules

The rules below are binding for the whole repository.

## Ownership And Boundaries

- **[STRICT]** The app holds two credentials, each in a Keychain item of its own (iOS App): the Revyl key from the person's Revyl sign-in, and the tokens of their GitHub sign-in. The GitHub token reads and writes GitHub directly, and the only other place it goes is the build's Revyl backend: the refresh token to renew the sign-in, and the access token to connect the GitHub account to the Revyl account and with settings and data deletion requests. The Revyl key goes only to the build's Revyl backend: to read and set the GitHub connection, to sign out, to delete the Revyl account, and with a request for a video that backend hosts (Signed Media URLs). The demo is read through Revyl's backend with no credential (Demo Mode), and the app reads no Revyl product database directly.
- **[STRICT]** GitHub is the record for pull requests, weekly and feature videos, media, comments, reactions and vibes. The viewer's changes to one reaction on one pull request, week, feature or comment reach GitHub in the order they were tapped, and only the newest one failing undoes what the app shows. Revyl's backend holds only what GitHub can't: the Revyl account and its keys, the GitHub account each Revyl account connected, the redemption and refresh of the GitHub sign-in with Revyl's GitHub App, which both need the App's client secret, and each person's settings, keyed by the numeric GitHub user ID it reads from the GitHub token on every settings request. It stores no GitHub token and never proxies a GitHub write or a person's GitHub read. Its own GitHub reads for the app are the demo feed (Demo Mode), the account behind a GitHub token it connects, and, before a hosted video from a private repository plays, whether the connected GitHub account can read that repository (Signed Media URLs).
- **[STRICT]** The only way into the app is Revyl's sign-in, and GitHub's sign-in only connects a GitHub account to a Revyl account that is already signed in (Revyl Sign-In). The app has no sign-up, never creates a Revyl account or adds anyone to an organization, and has no test-only way around the sign-in.
- **[STRICT]** Delete my ShipTok data, offered once GitHub is connected, removes what ShipTok keeps for the person. Revyl's backend deletes their ShipTok settings and revokes the GitHub token the app presents; the app then asks Revyl to revoke its Revyl key, best effort, and deletes both Keychain items, its caches and its defaults, which signs it out of Revyl and GitHub. The Revyl account and its GitHub connection stay, and Delete my Revyl account removes them (Revyl Sign-In). Only that GitHub token is revoked, never the person's whole authorization of the GitHub App, which would also end every other Revyl surface on the same App. The deletion succeeds only once the Keychain lets both items go and the app's own caches (its saved feeds, saved media and URL cache) and defaults are gone; anything else iOS keeps under Caches is swept best effort. Comments, reactions and vibes are GitHub's record and stay there. Anything new the backend or the app keeps per person joins Delete my Revyl account in the same change, and Delete my ShipTok data too when only ShipTok uses it.
- **[STRICT]** Revyl's part of either deletion revokes the credentials it ran with, so it can't run twice. The moment Revyl confirms it, the app saves in its defaults which deletion it was and whether it still owes the GitHub token's revocation (Delete my Revyl account, Revyl Sign-In), and it never shows the revoked sign-in again. Until the iPhone's part finishes, each launch and each Revyl sign-in finishes the deletion before anything else: the revocation if it's still owed, then the iPhone's part, and then the first screen says which deletion finished, with the note to revoke Revyl's GitHub App when the revocation failed. When the iPhone's part fails, the first screen says the deletion is unfinished. A Delete my ShipTok data that the GitHub-only release left unfinished, saved under the person's GitHub user ID, finishes the same way.
- **[STRICT]** The ShipTok format is a contract shared with Revyl's pull request review config and the people who post ShipTok videos: which pull requests are in the feed, the ShipTok video marker and tag, which media shows first, the vibe comment, and the weekly edition and feature issues, all documented in `docs/shiptok-format.md`. The parser and the vibe comment change only together with that document. Hidden `<!-- shiptok:... -->` markers are read from the raw markdown body, since GitHub's rendered HTML drops them.
- **[STRICT]** Comments are the top-level conversation comments people post on a pull request or on a week's or a feature's issue. Bot comments, inline code-review comments and every comment carrying a ShipTok tag never show as comments, with or without a video, while media from any top-level comment, a bot's included, counts.
- **[STRICT]** A ShipTok video is a video in a description or a top-level comment tagged with `#shiptok`, in any case, or `<!-- shiptok:video -->`. The marker's attributes are ignored, and neither who posted the video nor where it's hosted changes what the tag means. The newest tagged video plays first, ahead of other media. People make videos with their own tools, and the app never requires or infers that Revyl made one.

## Revyl Sign-In

- **[STRICT]** Nothing shows without a Revyl sign-in, the demo included. With no Revyl key in the Keychain, the app shows the first screen, which offers exactly two choices: Sign in to Revyl and Join existing organization. Another way into the app, or another choice on that screen, needs a product decision first.
- **[STRICT]** Sign in to Revyl first finishes any deletion left unfinished (Ownership And Boundaries). It then asks the build's Revyl backend for Revyl's sign-in link (`GET /revyl-sign-in/authorization-url`, with a random state and a PKCE S256 challenge) and opens it in an ephemeral web authentication session (iOS App). Revyl's page has no sign-up and returns to `shiptok://revyl-sign-in-callback` with a single-use code. The app takes the code only when the state matches and exchanges it, with its verifier and the device label `ShipTok on <device model>`, for a Revyl key (`POST /revyl-sign-in/api-keys`); `revyl_sign_in_expired` asks the person to sign in again. The key doesn't expire on its own and is kept only in the Keychain. An account in no organization gets Revyl's join choices on that page instead of a callback, and closing the page reads as a cancel, so the first screen stays as it was.
- **[STRICT]** Revyl's refusals carry `{"detail": {"error", "key"}}`, and only the key says which refusal it is, never the status. Any route the Revyl key goes to may answer `revyl_sign_in_required` (401), for a key Revyl no longer takes, or `revyl_organization_required` (403), for an account that left every organization. Either ends the Revyl sign-in wherever the person is: the app forgets the key and shows the first screen saying why, opened on Join existing organization for `revyl_organization_required`, and for that one it also asks Revyl to revoke the key, which may still be live. The GitHub sign-in stays on the iPhone, so the next Revyl sign-in connects it again. Any route a GitHub token goes to may answer `github_sign_in_rejected` (401), Revyl relaying GitHub's refusal of that token, which the app handles as GitHub refusing it (iOS App). Any refusal the app doesn't recognize, a 401 without one of these keys included, is an unexpected answer that ends neither sign-in.
- **[STRICT]** Signed in to Revyl, a person whose GitHub account is connected sees their own feed, and one without looks around the demo (Demo Mode). Revyl keeps one GitHub account per Revyl account and one Revyl account per GitHub account, and the latest connection wins. Connect GitHub first offers Revyl the GitHub sign-in the iPhone already holds, from an app that signed in with GitHub alone or from a Revyl sign-in that ended (`PUT /github-account` with the GitHub token, from which Revyl reads the account). Only when there is none, or GitHub refuses it, does it open GitHub's own sign-in, in the same kind of ephemeral session, and connect the sign-in that completes the same way. Once Revyl connects it, the person lands in their own feed, and a failure keeps them where they were, saying why. A Revyl sign-in connects a GitHub sign-in the iPhone holds the same way before it shows anything, and opens the demo, saying why, when that fails.
- **[STRICT]** While the app sleeps, Revyl can end the sign-in, the account can leave every organization, and its GitHub connection can move to another Revyl account, so the app asks `GET /github-account` at every launch and every return to the foreground. In the person's own feed, an answer of no connected GitHub account (`github_account_not_connected`) or of another GitHub account leaves the feed for the demo. In the demo, an answer naming the GitHub account whose sign-in the iPhone holds opens the feed, since a connection whose answer was lost went through. A hosted video refused for the Revyl sign-in asks the same question (Signed Media URLs).
- **[STRICT]** GitHub refusing the GitHub sign-in ends only that part: the app forgets it, and the person stays signed in to Revyl in the demo until they connect GitHub again. Whenever the person leaves their own feed for the demo, the demo's Settings and its Connect GitHub sheet say why, and a GitHub sign-in the iPhone still holds connects again in one tap.
- **[STRICT]** Every account menu (Settings, the demo's Settings, and the Account sheet of the Connect GitHub screen and of the repository picker) holds Sign out and Delete my Revyl account, and Delete my ShipTok data once GitHub is connected. Sign out asks Revyl to revoke the key (`DELETE /revyl-sign-in/api-key`), best effort, and ends only once the Keychain lets both the Revyl key and the GitHub sign-in go, since an item it kept would come back on the next launch. The feed's reads and saves stop and drain before the feed ends (Feed Caching). Sign out, the two deletions and Connect GitHub never overlap: none starts while another runs, and the account menus disable Sign out and both deletions until it ends, since a connection saves the GitHub sign-in and sends the Revyl key after a sign-out or deletion would already have ended them.
- **[STRICT]** Join existing organization offers both ways to join: asking the organization's owner or an admin for Revyl's invite, which the person accepts from their email before signing in, and an email field whose Submit sends `POST /organization-join-requests` with the address alone, so that Revyl emails the owners and admins of that address's organization asking them to invite it. Revyl answers 202 whatever it found, so the app shows one neutral confirmation naming the address and never says whether an organization matched; 422 says the address doesn't look like one, and 429 asks to try again in a minute. The address is shown on that screen and sent nowhere else: never logged, saved or put in analytics.
- **[STRICT]** Delete my Revyl account is the App Store's in-app account deletion (guideline 5.1.1(v)). `DELETE /revyl-account` with the Revyl key deletes the Revyl account with its memberships and keys, its GitHub connection and that GitHub account's ShipTok settings, and answers an owner of any organization with 409 `revyl_account_owns_organization`, whose `error` the app shows. Once Revyl confirms, the app saves the deletion as still owing the GitHub token's revocation, whether or not the iPhone holds a GitHub sign-in (Ownership And Boundaries), then revokes the token it holds, if any, with `DELETE /user-data`. A token GitHub already refuses leaves nothing to revoke; any other failure tells the person to revoke Revyl's GitHub App under Applications in their GitHub settings, since Revyl's part can't run again. It then finishes on the iPhone as Delete my ShipTok data does.
- **[STRICT]** An app that signed in with GitHub alone, once updated, opens on the first screen with a note naming the GitHub account it keeps, and its first Revyl sign-in connects that account.

## Demo Mode

- **[STRICT]** A person signed in to Revyl without a connected GitHub account looks around a read-only demo of one public repository, so App Review and the Revyl journeys can use the app with a Revyl account alone. Nobody reaches the demo without a Revyl sign-in. Revyl's backend serves it from `GET /api/v1/shiptok/demo-feed`, which takes no credential and allows 60 requests a minute per client address. It builds the demo from one GraphQL query it owns, plus further pages of comments for an item with more than 100, of the repository `SHIPTOK_DEMO_REPOSITORY_FULL_NAME` names in each environment, reads it with the token of Revyl's GitHub App installation on that repository's owner, and holds it for 60 seconds per process. It never takes a query or a repository from a client and never searches. It answers 503 when the repository is unset, missing or private or GitHub refuses, and the app then shows the Connect GitHub screen saying why, with Connect GitHub, Try the demo again and the Account sheet.
- **[STRICT]** The demo is a snapshot: the repository's 50 most recently updated open pull requests and 50 most recently updated merged ones, and its 25 most recently created closed issues labeled `shiptok-weekly` (`weekly_edition_issues`) and 25 labeled `shiptok-feature` (`feature_issues`), each with its comments. The app checks the issues against the weekly and feature formats and sorts them as Weekly and Features do. A snapshot without `open_pull_requests` lists none, so Open is empty, and one without `feature_issues`, from a backend older than Features, lists no features, so Features is empty while the rest of the demo works. A pull request without an update time sorts by when it was created, and a feature issue without `closedAt` is left out. GitHub signs a snapshot's media links for only minutes, so the app reuses a snapshot for 15 seconds and fetches a new one for the first read it needs after that; nothing reads the snapshot on a timer of its own.
- **[STRICT]** Open's and Merged's first page is the snapshot's whole list for that mode, except that Merged leaves out a pull request merged in the current second, which the next refresh brings in. Neither has older pages, and its end page says the viewer has seen every pull request in this demo, never every one in the repository. Every refresh makes the mode's list match the latest snapshot: a card the snapshot no longer holds leaves, the one under the viewer's finger once they move on (Feed Order), and every card it holds takes the snapshot's fresh media links, except that the card in focus keeps its own, apart from any whose load failed, so a playing video isn't reloaded. A read by number, of the card in focus or of a deck's pull requests, comes from the same snapshot, so a pull request outside it counts as gone and a deck leaves it out. Weekly shows the snapshot's weeks and Features its features.
- **[STRICT]** Everything that posts to GitHub as the person (likes, reactions, comments, vibes and their spoken feedback) and everything that needs a GitHub account (Report and the inbox) asks a demo visitor to connect GitHub instead, through a sheet whose Connect GitHub runs the connection (Revyl Sign-In), and a new write surface does the same in the change that adds it. A Connect GitHub button in the row under the mode switch (Card Layout) opens the same sheet, so the way to the person's own feed always shows. Hide, the mode switch, Videos only and playback speed work for the rest of the visit and are kept only in memory. The demo's Settings says it's a demo and offers Connect GitHub, with why the last connection failed, beside the account menu (Revyl Sign-In). Nothing of the visit is saved but media files, in the folder demo visits share (Feed Caching), and the visit's requests carry no credential. Connecting GitHub stops the visit's feed reads and lands in the person's own feed.

## Report And Hide

- **[STRICT]** Everything people post that ShipTok shows can be reported and its poster hidden, as App Store guideline 1.2 requires of an app that shows user-generated content. Report opens GitHub's own report form for that pull request, week's or feature's issue, or comment, since GitHub hosts the content and acts on reports, and ShipTok sends and keeps no report of its own. GitHub's form takes no reaction, so someone shown only for a reaction can be hidden but not reported. Hide takes everything the person wrote or posted (their pull requests, weeks, features, comments, vibes and media) out of the feed, decks, comment sheets, detail sheet and inbox for the viewer. It filters what is shown, never what is saved or fetched, so Unhide brings everything back at once.
- **[STRICT]** Hidden people are kept by GitHub login: on the device for each connected GitHub account in a person's own feed, and only in memory for a demo visit. Settings lists them with Unhide, and Delete my ShipTok data and Delete my Revyl account clear them with the app's other defaults. A new surface that shows what people post honors the hidden list and offers Report and Hide in the same change.

## iOS App

- **[STRICT]** `scripts/revyl/remote-build.sh` (`setup` / `compile` / `zip` / `upload-to-testflight`) is the only build pipeline; never fork a second one.
- **[STRICT]** ShipTok belongs to Revyl's Apple team, Revyl, Inc (`9MQ4RWNL3N`), and to no other: the project's `DEVELOPMENT_TEAM` and `upload-to-testflight` both name it. Its bundle id `ai.revyl.shiptok` is the app's only one, and extensions and app groups use `ai.revyl.shiptok.<suffix>`.
- **[STRICT]** `upload-to-testflight` takes the team's App Store Connect API key from its environment at run time and keeps it only in a temporary file it deletes, so the key never enters the repository. It archives unsigned and lets the export sign with Revyl's cloud-managed distribution certificate, so never add a signing identity, certificate or another team's key to a machine or the repository for it.
- **[STRICT]** The Xcode project uses a synchronized folder: files under `ShipTok/` join the target on their own, so never add per-file entries to `project.pbxproj`.
- **[STRICT]** The app holds only public configuration: the Revyl backend URL its build names and PostHog's project ingestion key. Debug and Release builds both use Revyl's production backend unless the `SHIPTOK_REVYL_BACKEND_URL` build setting names another, such as a development backend with its own GitHub App. The GitHub App client secret, PostHog personal keys and database credentials never enter the app or git.
- **[STRICT]** Each backend has its own GitHub App and its own Revyl keys, so a sign-in from one backend is never offered to another. Device tests and development point Debug builds at other backends, so a Debug build names both Keychain items after its backend's origin (`github-sign-in-test@<origin>` and `revyl-sign-in-test@<origin>`). Release builds ship pointed at production and keep `github-sign-in` and `revyl-sign-in`; the GitHub-only release kept its GitHub sign-in under `github-sign-in`, so renaming either would lose the sign-in of every iPhone that updates.
- **[STRICT]** The Revyl key, GitHub access and refresh tokens, sign-in codes and verifiers, signed media URLs and tokened Revyl media URLs are credentials. Never log, render, copy or persist them outside the Keychain. Requests to Revyl's ShipTok API carry them, so they never follow a redirect, and a 3xx answer is an unexpected one; GitHub API requests follow a redirect only over HTTPS to `api.github.com`, and a hosted video follows its redirect without the Revyl key (Signed Media URLs).
- **[STRICT]** Both sign-ins, Revyl's and GitHub's, run in an ephemeral web authentication session. A shared session first shows iOS's "wants to use … to sign in" prompt, and on an unfolded iPhone Duo continuing from that prompt tears the sheet down before it appears, so the sign-in silently does nothing there.
- **[STRICT]** A GitHub sign-in lasts until GitHub refuses to refresh it. A GitHub App user access token expires after eight hours and its refresh token works once, so the app refreshes ahead of expiry, and once when GitHub, or Revyl with `github_sign_in_rejected`, refuses a token another refresh may have retired: one refresh at a time, saving the rotated pair to the Keychain before anyone uses it. A pair the Keychain fails to save stays in memory and is saved again before use, never refreshed anew, since its refresh token is the only one GitHub still honors. An App that doesn't expire its tokens keeps one until GitHub rejects it. A refusal ends only the GitHub sign-in whose request it answered, never a later one, and a hosted video's refusal ends none (Signed Media URLs). The Revyl key never expires, and only Revyl's refusals end it (Revyl Sign-In).
- **[STRICT]** `ShipTok/PrivacyInfo.xcprivacy` declares the data the app sends off the phone, the email address a join request sends included, and its required-reason API uses, and the ShipTok section of Revyl's privacy policy (https://revyl.com/privacy/#shiptok) describes that data to people. A change that sends a new kind of data to Revyl, PostHog or GitHub updates both in the same change, and one that uses another required-reason API, even on data that never leaves the phone, updates the manifest.
- **[STRICT]** Test phones that connect GitHub use a build pointed at a development backend. GitHub keeps at most ten tokens per person for one app and revokes one of them for each sign-in past that, so every GitHub sign-in through Revyl's production GitHub App spends one of that person's ten.
- **[STRICT]** The feed's repository is the person's choice among every repository their GitHub sign-in reaches, meaning where an organization installed the build's GitHub App and the person has access, with no other allowlist; Debug and Release share one picker. The choice is remembered for each GitHub account, and with none the app opens RevylAI/shiptok-demo, the demo's public repository, when it's reachable, else the picker. A repository the App stops reaching sends the person back to the picker and never ends a sign-in. Each API client keeps its repository fixed, and changing the choice rebuilds the feed, Weekly, Features and inbox state; saved feeds and inbox read positions are scoped by repository and person.

## Product Analytics

- **[STRICT]** Capture native product facts through the typed boundary in `ShipTok/Analytics/`, whose typed events are the event contract. Keep delivery independent of product success, and record a GitHub write's success only after GitHub confirms it.
- **[STRICT]** In a person's own feed, events use the numeric GitHub user ID saved with the GitHub sign-in as their identity. The app never learns who signs in to Revyl, so each showing of the first screen has an ID of its own, which its events, the Revyl sign-in attempts and Join existing organization started there included, carry as `first_screen_visit_id`. A demo visit's events use the visit's own ID, carried as `demo_visit_id`, and a GitHub sign-in started from the visit carries that ID to its completion. Until GitHub names the person, a GitHub sign-in attempt's events use the attempt's own ID, which its completion carries. Revyl's backend records the outcomes it confirms itself (`shiptok_app_signed_in`, `shiptok_github_account_connected` and `shiptok_revyl_account_deleted`), so the app sends no event of its own for them. A login is renameable, and a repository owner is not a Revyl person or organization mapping. Events never let PostHog derive a location. Debug and Release use the web app's PostHog project, separated by `environment=development` and `environment=production` respectively.
- **[STRICT]** A watch starts only while a visible, foreground video is actually playing, never on mount, preload or download. Accumulate only playing time, leaving out pauses, buffering, scrubbing and comment-sheet occlusion, and summarize on leaving the video instead of emitting frame or loop events. Analytics visibility must not change playback behavior. Report a terminal playback failure only once the media-renewal path is exhausted, never for an expected first URL expiry. Never send media URLs or media IDs, tokens, titles, comments, feedback text, email addresses or other content. Subject and source-comment IDs are correlation keys, not breakdown dimensions. No repository name, and nothing that identifies a person the viewer reports or hides, enters analytics.
- **[STRICT]** An event about a card names it with `subject_kind` (`pull_request`, `weekly_edition` or `feature`), `subject_id` and `subject_number`, the pull request's or issue's number, and the mode switch's event names the mode it left and the one chosen in `previous_feed_mode` and `feed_mode` (`open`, `merged`, `weekly` or `features`). Every event carries `schema_version`, now 5. A new value of an existing property doesn't move it; adding or removing a property, or changing what one means, does.

## Card Layout

- **[STRICT]** Every screen follows Instagram Reels on the unfolded iPhone Duo held taller than wide, and other windows keep the same look. A feed page is a media card with small rounded corners running from at most 30 points below the top of the screen to 30 points above a floating pill tab bar. When two 84-point columns, wider where the system's trailing strip is, leave the card at least as wide as a 9:16 video of its height, the card sits centered between them with the action rail in the right column, so the leading column never narrows a Reels video. Otherwise a trailing system strip at least 56 points wide holds the rail beside the card, as on the folded Duo, and failing that the card spans the window with 8-point margins and the rail sits over its trailing edge, as on other iPhones. The rail starts below every region the system reports covering its column, such as the Duo's status strip with an expanded island or Live Activity, and its gaps shrink to fit the space left, down to overlapping the padding around its glyphs. Placement reads only the window's size, its safe area and those reported regions, never the device model or orientation.
- **[STRICT]** The rail holds plain glyphs with their counts: like, where a long press opens every reaction; comments; react; vibes (good, bad, and removing your own); mute and playback speed for a video that loads; the deck, on a pull request with more than one item or a still or GIF hero and on every week and feature, where it opens the pull requests the card names; and last, More, whenever the card shows something someone else posted (Report And Hide). Speed, also among the deck's controls, cycles 1x, 1.5x and 2x for every video, remembered on the device, or for the visit in the demo. The Open / Merged / Weekly / Features switch sits over the card's top left, inside the format's top safe zone. While a week's or a feature's pull requests are open, a back button takes its place: "Week of" with the week's dates for a week, and "Features" for a feature, whose title can run too long for the button. One row sits 8 points under the switch, aligned with its left edge and clear of its taps: a demo visitor's Connect GitHub (Demo Mode), then the "new" pill (Feed Order), 8 points apart, so neither covers the switch or the other however wide the switch grows. The caption sits over the card's lower left above a thin video progress line. The tab bar holds the feed, the inbox and settings, and the inbox and settings replace the feed while its video is paused.
- **[STRICT]** The hero never loses more of itself than the card's shape forces. A shape that loses at most an eighth of itself filling the card crops to fill it, as a 9:16 video does on other iPhones and on the unfolded Duo held tall. Every other shape, a wide screenshot or GIF on a tall card included, shows whole and centered over a blurred copy of itself, so there are never black bars and no part of a screenshot is cut off.
- **[STRICT]** Text on a card stays short. A pull request shows its author, the viewer's own vibe badge, a title of at most two lines, and its number with when it merged ("merged 2 days ago") or, while open, when it was last updated ("updated 2 hours ago", after "Draft · " on a draft). A week shows its "ShipTok weekly" chip, dates, title and hook in place of the author, number and time, and a feature its "ShipTok feature" chip, when its issue closed ("shipped 3 days ago"), title and hook; on both, the title and the hook take at most two lines each. The rest (the description, stats, labels, and everyone's vibe and reaction counts) is one tap away in the detail sheet, which says when the pull request merged, or that it's open or a draft and when it was last updated, and the swipe legend lives in Settings. A pull request with no media is the one card that shows its description, stats and labels (below).
- **[STRICT]** A pull request with no media, which only a feature's deck shows (Features Mode), puts a summary where its media would be: its state (Merged, Open or Draft), its additions, deletions and changed files, its labels, its description or "No description.", and a Details button that opens the detail sheet. The summary stays inside the band where a ShipTok video keeps everything a viewer must read, from 322/1920 of the card's height down to 1376/1920, or to 16 points above the caption when that's higher, left of the rail and no wider than the readable column, so the switch, back button, rail and caption never cover it, and a description too long for the band fades out at its bottom. Only the Details button takes a tap there, so a double tap anywhere else on the card still likes it and no link in the description opens from the card. The summary hides with the caption while the reaction picker, the feedback box's keyboard or a playback gesture is up.

## Feed Order

- **[STRICT]** Open and Merged each hold the chosen repository's pull requests that carry media (`docs/shiptok-format.md`), at any age, with no time window, label or grouping. Open holds the open ones, drafts included, most recently updated first, and Merged the merged ones, most recently merged first, with ties going to the higher number. A pull request closed without merging is in neither. Each mode reads its newest page first and reads older pages as the viewer scrolls, until the repository has none left.
- **[STRICT]** Open reads the repository's open pull requests 25 at a time through its pull request list ordered by update, never through search, and once the list has no next page it holds every one. Merged reads windows of merge dates going back from its cursor, which is the whole second where the last window it read begins, or the moment its first page loads. One request counts the merged pull requests in spans ending at the cursor (6 hours, a day, 3 days, a week, 2 weeks, 30 days, 90 days, a year, and everything older), and the window is the widest span holding at most 50, or the 6-hour span when none does. Merged reads the window whole through search, splitting it at whole seconds into ranges read in parallel while a range holds more than 125, and pages a range one second long whole, as far as the 1,000 results GitHub search gives one query, so it misses pull requests only when more than 1,000 merged in one second. Only a window read whole moves the cursor to its start, so a window another mode cut short moves nothing, and once the span with no start is read, Merged holds every merged pull request and has no cursor.
- **[STRICT]** Older pull requests load once the viewer is 5 or fewer shown cards from a mode's end, its end page included, and pages keep loading until 10 more cards show, nothing older is left or the mode leaves the screen. Both counts are of the cards the viewer is shown after Hide and Videos only, and the analytics event for each older page records how many pull requests it added and how many of those the viewer is shown. Each page is sorted and put below every loaded card, so nothing moves under the viewer: a card on it updated after the cards below it were read takes its slot like a newly found one, and a pull request already loaded updates in place. The viewer's card keeps its place as cards arrive or leave around it, and on the end page the viewer stays just past every card they had, so the first older card to load is the one they see next.
- **[STRICT]** Videos only is a person's setting, on by default. While it's on, Open and Merged show only pull requests whose first media item, once hidden people's media is left out, is a video; while it's off, ones whose first media is a screenshot or GIF show too. Weekly, Features and a deck show every week, feature and pull request either way. Like Hide, it filters what is shown and never what is read or saved, so turning it off brings cards back at once, and turning it on near a mode's end loads more once the mode is on screen. In a person's own feed the choice goes to Revyl's backend with their other settings as `shows_only_pull_requests_with_videos`, and saved settings without it read as on; a demo visit's choice lasts for the visit. The app shows the settings Revyl last confirmed, with each setting's newest change on top while it saves. A read of the settings updates only the confirmed ones and is dropped if a save succeeded while it ran. Saves run one at a time, each sending every setting as it stands when its turn comes, and a save settles its setting only when no newer change to that setting followed it, so a failed save shows the confirmed value again unless a newer change is still saving.
- **[STRICT]** An iOS app always shows the newest data it has, so while the Feed tab is selected the mode on screen reads GitHub again when it shows, when the app returns to the foreground, 10 seconds after its last read finishes, and on a pull from its first card. Inbox and Settings take the mode or a deck off the screen: its reads, focus, older pages, the deck's loading and media link renewals stop, what waited on the viewer settles (below), and coming back focuses the card the viewer is on and carries the deck's loading on from where it stopped. A refresh first reads the card in focus in full. Open then lists the repository's closed and merged pull requests updated since its last refresh, with 3 minutes of overlap, which leave Open, and then the open ones updated since, with the same overlap. Merged lists the merged pull requests updated since its last refresh, with the same overlap, through the repository's pull request list ordered by update, never search, and keeps those merged since its cursor, or all of them once it holds every merged pull request. Each mode reads in full by id, 25 at a time, the listed pull requests it hasn't already taken in at that update and merge date (Feed Caching), and applies each batch before reading the next, so a failed batch loses nothing read before it. A card coming into focus is read again, renewing its media links when they're more than 2 minutes old, and the next card the viewer is shown has its links renewed once they are. Older pages, the reads around the card in focus and the read that renews a pull request's failed media link belong to what's on screen and stop when it leaves; a failure recorded while neither a mode nor a deck is on screen waits for the next read (Signed Media URLs).
- **[STRICT]** When GitHub throttles the person's GitHub account, the app asks GitHub nothing more, from any screen, until the time GitHub's `Retry-After` header gives, else until `X-RateLimit-Reset` when the hourly quota is used up, else for 60 seconds. A throttle is a 429, a 403 that says the quota is used up, carries `Retry-After` or names a secondary rate limit, or a GraphQL `RATE_LIMITED` error inside an answer GitHub sends as successful, and any answer saying the quota is used up starts the same wait. Every other refusal is an ordinary failure.
- **[STRICT]** A pull request found after a mode opened, or one whose update changes its slot, takes its sorted slot. At or above the card in focus it's flagged for the "new" pill, which counts such cards and jumps to the first of them. Below, it never lands above or between the card in focus and the next card the viewer is shown, since both are already rendered, and waits just after them until the viewer moves to another page; a card the viewer isn't shown, hidden or filtered out by Videos only, doesn't count as that next card. Those two cards keep their slots when they change and move once the viewer moves on, and the card the viewer just left moves without the pill. One sorting below every loaded card waits for its own page unless it may go last: in Open once Open holds every open pull request or has none, and in Merged when it merged at or after the cursor.
- **[STRICT]** A card that stops belonging to its mode leaves it: an open pull request that merges or closes, one GitHub no longer has open or merged, or one left with no media. The card under the viewer's finger stays until they move to another page or the mode leaves the screen, and so does the copy of it they see: a fresh read they wouldn't be shown, with no media left to show or, under Videos only, no video first, waits and takes its place once they move on, and a later read they can be shown cancels the wait. Hiding a person and changing Videos only still apply to that card at once, and being told the same page again changes nothing. When a mode leaves the screen, for another mode, a deck, Inbox or Settings, what waited on the viewer settles: a leaving card goes, a waiting copy takes its card's place and held cards take their slots, while the viewer keeps their place, moving to the next card when their own leaves. Off screen, a card that leaves goes at once.
- **[STRICT]** A pull request is dead for a viewer once every media item it holds, hidden people's included, is given up: refused to them, or failed again from a renewed URL (Signed Media URLs). One with no media left isn't dead; it leaves as above. One whose media the viewer can see is all given up while a hidden person's isn't is out of their sight instead, the way Hide leaves cards out: every mode and an open deck leave it out at once, the card under the viewer's finger included, and it comes back once Unhide brings media that isn't given up into view. A dead pull request leaves every mode and an open deck the way a card that stops belonging does: at once, except the card under the viewer's finger, which goes once they move off it. A card a mode or a deck opened on, that the viewer hasn't moved off, goes at once instead, so the viewer lands on the next card they're shown, or past the last card when none is left. A mode the viewer comes back to, from another mode or tab, counts as opening on the card it shows, and a deck counts as opening only when its week's or feature's pull requests open. On a card the viewer has reached, and on a deck page, media that's given up says its video or image is unavailable; until then it keeps the loading look.

## Feed Caching

- **[STRICT]** Open and Merged are saved on the device for the repository and the GitHub login of a person's own feed, never for a demo visit, when the app goes to the background, before the person picks another repository, and after older pull requests load. Each is saved with the moment every update before it was applied, Merged also with its cursor, or the fact that it holds every merged pull request, and Open with GitHub's cursor for its next page, or the fact that it holds every open one. Each card is saved as it will stand once the viewer moves on (Feed Order). A launch opens on the saved feeds at once, however old they are, keeping the cards that still belong to their mode in feed order, and each mode then refreshes from the moment every update before its saved feed was applied.
- **[STRICT]** Each mode records, for every pull request it takes in from a read or a page, the update and merge date it took, and its refresh doesn't read a listed pull request again when it already took it at both, so one read as open that merged in the same second is still read for Merged. The record lasts for the app session and isn't saved or rebuilt from the saved feeds, so the first refresh after a launch reads in full every pull request its lists keep, among them any from the 3-minute overlap that still qualifies for the mode, even one the saved feed already holds at that update. Some reads always happen: the card in focus is read in full on every refresh and whenever it comes into focus, the next card the viewer is shown is read again when its media links are due for renewal, and Weekly, Features and an open deck read GitHub afresh each time. Comments, reactions and vibes stay live through the card in focus.
- **[STRICT]** The saved feeds carry a format version, now 8. Reading them decodes every saved file and deletes each one that doesn't decode or holds another version, whoever's it is, so a change to what's saved, or to a check below that decides it, moves the version. Feeds saved before Open existed sit in a folder of their own, which every launch deletes in the background and both deletions remove with the app's other caches.
- **[STRICT]** A saved feed holds no signed media URL, tokened Revyl media URL, description, comment or rendered HTML. The free text it keeps, titles and label names, is redacted when the pull request is read, as on every surface that shows it (Signed Media URLs). A saved media item keeps its URL only when the URL isn't a credential, so its media plays from the device or waits for the card in focus to be read again. A tokened Revyl media item's id is a hash of its canonical URL, never the token or the redirect target. Open's next page is saved as GitHub's list cursor, which holds no credential.
- **[STRICT]** The feed's reads and saves belong to one viewer, a person's own feed or a demo visit. Sign out, Delete my ShipTok data and Delete my Revyl account stop a person's own feed's and wait for what's running before they go on, and a save its ending cancelled writes nothing, so nothing read for that feed is saved after it ends. Anything else that ends it, a refusal from GitHub or Revyl or a GitHub account no longer connected (Revyl Sign-In), stops its reads and saves at once. Connecting GitHub and every way out of the demo stop a demo visit's.
- **[STRICT]** Media is kept per viewer, since a private repository's media is only for people who can read it. A person's own feed has its own loaded images and videos, failed loads and downloads, and saves its files in a folder named for their GitHub user ID (`github-user-<id>`), while demo visits share the folder `demo`. A load takes its viewer's media cache before it awaits anything and keeps what it gets only there, so no viewer ever reads another's media, however late a cleanup lands or if it fails. Saved files are named by a hash of their media item's id and play from the device on later launches. The modes, weeks, features, decks and the demo share their viewer's files, so a file goes once it has gone 30 days without being saved or shown, never by one surface's list. When a person's own feed ends (Revyl Sign-In), its downloads stop unsaved and its loaded media and folder go as cleanup, and a demo visit that ends for anything but connecting GitHub does the same with its own; both deletions remove every viewer's saved media.

## Feed Modes

- **[STRICT]** The feed has four modes, Open, Merged, Weekly and Features, switched at the card's top left. It opens on Merged the first time and then on the mode the person last chose, remembered on the device, or only in memory for a demo visit; a stored mode it doesn't know opens Merged. Each mode, and a week's or a feature's deck while it's open, keeps its own place and its own loading, failure, end and empty pages. Opening a week's or a feature's pull requests replaces the switch with a back button to its list (Card Layout), and only one deck is open at a time.

## Weekly Mode

- **[STRICT]** Weekly shows one card per closed issue in the chosen repository labeled `shiptok-weekly` whose description follows the weekly format in `docs/shiptok-format.md` and that carries media, newest week first, so two issues for one week are two cards. Its media can be untagged, and images and GIFs count: the card plays its newest tagged video, else its first video, else its first image or GIF. The app lists the closed issues with the label through the issues API, never search, 25 at a time, most recently created first, until none are left, then leaves out a description outside the format or an issue with no media and sorts the rest by week. A week shows on the first read after its issue closes.
- **[STRICT]** A week's deck shows its open and merged pull requests that carry media (Pull Request Decks).

## Features Mode

- **[STRICT]** Features shows one card per shipped feature, however many pull requests shipped it: a closed issue in the chosen repository labeled `shiptok-feature` whose description follows the feature format in `docs/shiptok-format.md` ("Features") and that carries media. Its media can be untagged, and images and GIFs count, as on a week. The app lists the closed issues with the label as Weekly does, through the issues API, never search, 25 at a time, most recently created first, until none are left, then leaves out a description outside the format or an issue with no media and sorts the rest by when each issue closed, newest first, then by the higher issue number, so each issue is a card of its own. A feature shows on the first read after its issue closes and dates from that close; reopening the issue takes its card away at the next read, and closing it again dates it from the new close.
- **[STRICT]** A feature's deck shows every open or merged pull request its description lists, with or without media of its own, since the feature's video is the card and the deck is the work behind it; one with no media shows as a summary (Card Layout). Otherwise it reads and shows them as a week's deck does (Pull Request Decks).

## Published Issues

- **[STRICT]** A week and a feature are each a published issue: a closed issue whose description gives a title, a hook and the pull requests behind its video, which ShipTok shows as a card (`docs/shiptok-format.md`). Each takes likes, reactions, comments and vibes on its issue exactly as a pull request does. The app never edits, reopens, closes, relabels or locks one; posting weeks and features is the poster's job, never the app's.
- **[STRICT]** Weekly's and Features' reads belong to the feed view, not to the mode reads of Feed Order: while either is on screen it reads its issues when it shows, when the app returns to the foreground, 10 seconds after its last read finishes and on a pull from its first card, and a card coming into focus more than 2 minutes after the last read reads them again, as does a card's failed media load, to renew its links, even with Inbox or Settings over the feed, unless the failure gives the item up at once (Signed Media URLs). The repeating reads stop when the mode leaves the screen, and a read a pull, a card coming into focus or a failed media load started runs to its end. A week or feature whose media is given up stays and says its video or image is unavailable; only pull request cards leave for dead media (Feed Order).

## Pull Request Decks

- **[STRICT]** A week's or a feature's deck opens the pull requests its description lists as ordinary pull request cards in the list's order, each with its own likes, reactions, comments and vibes, and shows each one whatever Videos only says, less what hidden people posted. They're read by number, since a list can name pull requests neither mode has loaded, 6 at a time, each joining the deck once every one before it is in, so a page never moves under the viewer. The deck reads them only while it's on screen: Inbox or Settings over it stops the reading and releases the deck's focus, letting a card waiting on the viewer go, and coming back carries on from the first pull request not yet in, at the viewer's place, while going back to the list closes the deck. One closed without merging or gone, and one dead for this viewer (Feed Order), is left out, and so is one with no media in a week's deck, though a feature's keeps it (Features Mode). One whose read fails shows the copy a mode will hold once the viewer moves on, if a mode has one and it isn't dead for this viewer.
- **[STRICT]** The deck's focus follows the card on the viewer's page: the first card to arrive takes it, the next card takes it when the one under the viewer leaves, and the end page focuses none. While a deck is open, the card in focus is read again when it comes into focus and 10 seconds after its last read finishes, the next card's media links are renewed when due, and a pull reads the first card the viewer is shown. A card leaves the deck when a read finds it closed without merging or gone, or, in a week's deck, with no media, the card in focus once the viewer moves on; a dead card leaves as Feed Order says, and the viewer's card keeps its place as cards leave around it. The card in focus keeps its media links, so a playing video isn't reloaded, unless they're more than 2 minutes old or failed to load.

## Signed Media URLs

- **[STRICT]** GitHub's upload URLs come from its rendered HTML, signed for the reader, and stop working a few minutes after the read. A Revyl-hosted video's canonical source is the video target in the raw description or comment, including when a poster links to it, and the poster is not another deck item. A media item's identity never includes its URL's query string. A video downloads once, in a single request and never past the size limit in `docs/shiptok-format.md`, and every replay, loops included, plays from memory.
- **[STRICT]** A fresh URL is fetched only after a load fails: a URL signed in its query string is renewed by reading the pull request again, and an unsigned one, such as a hosted video's tokened link that redirects to the file, by requesting it once more. A failed item is given up only once its renewed URL fails too, or once a read that started after the failure brings back the URL that failed; a failure no such read has settled yet waits for the next one, so a renewal that fails offline is settled once the app reads again.
- **[STRICT]** A hosted link is one whose path ends in the hosted video route and an upload's canonical name (`docs/shiptok-format.md`), under whatever path its backend is served from, and extraction recognizes one through the single check that says so. Media ids and saved feeds are broader on purpose: any link whose path holds the hosted video route, however it's escaped or cased, is a credential. Redaction never depends on reading a link: after keeping the labels of the links it can read, it removes from the text every run without spaces, quotes or brackets that holds the hosted video route followed by a token-shaped segment, relative or absolute, escaped, cased or bare, and keeps the prose punctuation (`.`, `,`, `;`, `:`, `!` or `?`) that trails it. A change to either check that could leave saved feeds holding a credential or a stale id moves their format version.
- **[STRICT]** A hosted video on a private repository plays only for a Revyl account in an organization whose connected GitHub account GitHub lets read the repository. So in a person's own feed a request for a hosted link carries their Revyl key as a bearer token, and only when the link's scheme, host and port are the build's Revyl backend and its path reads exactly as that backend's hosted video route and the upload, with no userinfo, escapes or dot segments. A link naming any other host carries no credential, and neither does any request a demo visit makes, so the demo plays only public repositories' hosted videos. A redirect goes only to HTTPS and carries no Authorization or cookie, since the file's link is signed in its query string and the Revyl key never leaves Revyl's backend, and it never replaces the canonical cache identity.
- **[STRICT]** A 401, 403 or 404 that the hosted video route answers itself, never one from where a redirect leads, is Revyl refusing the video to this viewer. The video is given up at once, with no renewed request or read, is never taken for an expired URL, and never ends a sign-in by itself. The app reads the refusal's body to its end: a 401, or the key `revyl_sign_in_required`, `revyl_organization_required` or `github_account_required`, refuses the Revyl sign-in rather than the video, so in a person's own feed the app asks `GET /github-account` where the sign-in stands and acts on that answer (Revyl Sign-In). Any other refusal refuses only that video.

## Vibes

- **[STRICT]** A person has one vibe per pull request, week or feature: a new vibe comment replaces their earlier vibe comments on it, and undoing it, from the toast or later from their own vibe badge or the rail's vibes button, deletes it.
- **[STRICT]** The vibe feedback box never blocks the swipe. The feed advances at once, the box is a per-person setting (on for bad vibes and off for good vibes by default), and feedback typed or spoken before the next swipe posts with its vibe.

## Swipe Gestures

- **[STRICT]** Swipe directions are a product decision: up shows the next card, down the previous one, right casts good vibes, left casts bad vibes, and a double-tap likes. A single tap on a playing video pauses it, showing a play glyph, and another tap resumes it; it waits out a double-tap, so a like never pauses, and the rail and caption keep their own taps. Change them only in the feed's swipe gesture mapping (`FeedSwipeGestureMapping`); the card stamp, settings, deck and the rail's vibes button read that mapping. Swapping directions within an axis is safe, while moving navigation to the horizontal axis needs deck layout changes.
- **[STRICT]** Holding a playing video past a tap's length plays it at 2x, with a "2x" hint, until the finger lifts and it returns to the chosen speed, and a sideways drag that starts on the strip around a hero's progress line, or on a deck page's line, scrubs it with a time readout, so neither costs a tap, double-tap, swipe or vibe, and neither reaches the tab bar or home indicator. The hold is UIKit's long press, since a SwiftUI long press on the video stops a single tap from pausing it, so it needs iOS 18; earlier systems keep the scrub.

## Revyl

- **[STRICT]** `.revyl/config.yaml` on `main` is the Revyl project's configuration. Revyl's GitHub App applies it on every push to `main` and refuses edits from the dashboard or `revyl config push`, so change it only in git, and run `revyl config validate` before committing it.
- **[STRICT]** `.revyl/tests/` holds one Revyl test per journey through the app and `.revyl/modules/` the steps they share. Runs read them from git (`run_test_definitions_from_git`), a pull request's runs at its head commit. A change to a journey updates its test in the same change, and a new journey gets a new test, added to the ShipTok journeys workflow `.revyl/config.yaml` names. Push a new or changed test or module with `revyl test push --include-modules-and-scripts` before committing it, and commit the `_meta` it writes, since `_meta.remote_id` ties the file to its test in Revyl.
- **[STRICT]** Every journey starts on the first screen. The two first-screen journeys stay signed out, and every other journey enters through the `shiptok-sign-in-to-revyl-and-open-demo-feed` module, which signs in to Revyl with the ShipTok test account and lands in the demo. Proof of changes (`.revyl/config.yaml`) and Atlas (`.github/workflows/ci.yml`) sign in the same way. The test account must be in exactly one organization, without MFA and with no GitHub account connected, so its sign-in needs no other step and always lands in the demo. Its email and password live only in the Revyl organization's secret global variables `shiptok-revyl-sign-in-email` and `shiptok-revyl-sign-in-password`, named as `{{global.<name>}}` and never written into the repository. No journey, proof or exploration connects GitHub, completes a GitHub sign-in, signs out or deletes anything.
- **[STRICT]** Every build CI uploads carries its repository, head commit, branch and pull request, which Revyl's proof of changes and pull request workflows find it by. `revyl build upload` reads them from GitHub Actions, so keep uploads on it.
- **[STRICT]** `.agents/skills/`, linked for Claude Code from `.claude/skills/`, holds Revyl-managed skills from `revyl skill install`. Never edit them in place; when the Revyl CLI version pinned in `.github/actions/install-revyl-cli/action.yml` moves, refresh them with `revyl skill update` from that version.

### Revyl Verification

When developing or changing a feature in this repo, use the Revyl dev loop to verify the behavior on a device before finishing.

- Read and follow the local `revyl-cli-dev-loop` skill (`.agents/skills/revyl-cli-dev-loop/SKILL.md`) before running Revyl commands. `revyl dev --remote --profile development --platform ios` builds the checkout on Revyl's cloud builder and opens it on a cloud iPhone, so it needs no Mac.
- Verify the user-visible outcome with device evidence, such as `revyl device screenshot`, `revyl device report --json`, or explicit interaction through `revyl device instruction`, and run the journey tests the change touches with `revyl test run <test name>`.

## CI And Releases

- **[STRICT]** `.github/workflows/ci.yml` runs on every pull request and push to `main`: a gitleaks scan with `.gitleaks.toml`, then `scripts/revyl/remote-build.sh` (`setup`, `compile`, `zip`) on GitHub's `xcode-27` runner with Xcode 27.2, uploading the build to Revyl. On `main` it runs the ShipTok journeys workflow on that exact build and explores it with Atlas, one exploration at a time with every build queued. Fork pull requests get no secrets, so they build without uploading.
- **[STRICT]** `main` works against Revyl's production backend at every commit, and its journeys run on a build that uses production, so they show whether it does. An app change that needs new backend behavior merges to `main` only once that behavior is live in production, and waits on its own branch until then: one named after the cognisim-monorepo pull request it ships with, `cognisim-<number>-<what it does>` (for example `cognisim-6944-open-and-merged-pull-request-feeds`), pushed so it shows on GitHub, and never merged to `main` before that pull request is live in production. The app relies only on what production serves, and Revyl's backend only adds to the ShipTok API, so an app already on `main` or in TestFlight keeps working beside a newer backend.
- **[STRICT]** `.revyl/config.yaml` is the only place that names the Revyl app and workflows: CI reads them from it with `revyl config show --json`, and the repository's GitHub settings hold only secrets.
- **[STRICT]** `.github/workflows/release.yml`, run by hand with a build number, is the only way builds reach App Store Connect: it runs `upload-to-testflight` with the App Store Connect API key in the repository secrets `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_API_ISSUER_ID` and `APP_STORE_CONNECT_API_PRIVATE_KEY`.
- **[STRICT]** This repository is public, and so are its Actions logs: no workflow prints a secret, token, internal hostname or customer data.
- **[STRICT]** Workflows pin every action to a commit and the Revyl CLI and gitleaks to a release version.
