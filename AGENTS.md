# ShipTok Guide For AI Contributors

This repository is ShipTok, Revyl's iPhone app (SwiftUI, iOS 17 and later). A person signs in with their Revyl account and watches a vertical feed, one card per swipe, of a repository their Revyl organization's GitHub App covers: its open pull requests with media in Open, its merged ones in Merged, one card per weekly video in Weekly and one per shipped feature in Features, where a week's or a feature's card opens the pull requests behind it. Revyl's backend serves all of it through its ShipTok API (`/api/v1/shiptok/`), which lives outside this repository: it reads GitHub through Revyl's GitHub App and keeps the likes, reactions, vibes, comments, inbox and settings people give in ShipTok.

---

# Guidance & Rules

The rules below are binding for the whole repository.

## Ownership And Boundaries

- **[STRICT]** The app talks to one backend: the Revyl backend its build names (iOS App), through the ShipTok API with the signed-in person's ShipTok key (`ShipTok/Auth/RevylShipTokAPI.swift`). It calls no GitHub API, holds no GitHub credential and reads no database. Its only other traffic is product analytics to PostHog (Product Analytics), the media links Revyl's posts carry (Signed Media URLs), and github.com pages it hands to the browser: a pull request's Open on GitHub and GitHub's report form (Report And Hide).
- **[STRICT]** Revyl's backend is the record for everything people do in ShipTok: likes and other reactions, vibes, comments and replies, inbox read state, each Revyl account's settings and GitHub username, and each organization's settings. GitHub is the record for the posts and their media, which the backend reads through the organization's installation of Revyl's GitHub App. The app never writes to GitHub; the backend's feedback summary comment is the only thing ShipTok feedback puts there (Settings).
- **[STRICT]** Revyl's backend parses the ShipTok format (`docs/shiptok-format.md`) and serves each post ready to show: its media in show order with the hero first, a week's or a feature's title, hook and deck numbers, and its description with HTML comments and bot blocks left out. The app shows those fields as served and never reads a description or comment for media, markers or a week's or a feature's format, so a change to what counts is a change to the backend and that document together.
- **[STRICT]** The iPhone keeps only the Keychain sign-in (Revyl Sign-In), the saved feeds and media (Feed Caching), the URL cache, and defaults such as the repository choice (Repositories), the hidden people (Report And Hide), the feed mode and the playback speed. Anything new that ShipTok keeps for a person, on Revyl or on the iPhone, joins Delete my Revyl account in the same change.
- **[STRICT]** Delete my Revyl account runs Revyl's part first and the iPhone's part second. Revyl's part revokes the key, so it can't run twice: once Revyl confirms, the app records `unfinished-revyl-account-deletion` in its defaults, then deletes the Keychain sign-in, the URL cache, the `post-feeds` and `post-media` caches and, best effort, everything else under Caches, and removes the whole defaults domain last, the record with it. A quit or a failure leaves the record, and the next launch, or the next sign-in before it starts, finishes only the iPhone's part.

## Revyl Sign-In

- **[STRICT]** Nothing in ShipTok works without a Revyl sign-in. The first screen (`ShipTok/Auth/FirstScreenView.swift`) offers exactly two ways on, Sign in to Revyl and Join existing organization, and the app itself creates no Revyl account. The person's sign-in alone opens their organization's repositories; nobody connects a GitHub account.
- **[STRICT]** Sign in to Revyl works like `revyl auth login`. The app reads Revyl's web sign-in page from `GET revyl-sign-in/authorization-url` with its own state and PKCE challenge, opens it in an ephemeral `ASWebAuthenticationSession` that returns to the `shiptok` scheme, and trades the single-use code and its verifier at `POST revyl-sign-in/api-keys`, with the device label "ShipTok on <model>", for a ShipTok key: a personal Revyl API key that Revyl marks as ShipTok's own, so signing out revokes exactly it. It then reads `GET revyl-account` and saves the key and the account together in the Keychain (iOS App).
- **[STRICT]** An account in no organization gets Revyl's join choices on the web sign-in page. Closing that page reaches the app as a cancelled sign-in, so the first screen stays as it was.
- **[STRICT]** Revyl's refusals carry `{"detail": {"error", "key"}}`, and the key, never the status alone, says which refusal it is. `revyl_sign_in_required`, `revyl_person_required` and `revyl_organization_required` refuse the sign-in itself, which no retry changes, and Revyl refusing the key on any route ends the sign-in that route ran for: a refused key leads to the first screen, and `revyl_organization_required` revokes the key, best effort, and opens Join existing organization. A 429 is rate limiting, and every other key is that route's own answer.
- **[STRICT]** A launch opens on the saved account at once, and each launch and each return to the foreground asks `GET revyl-account` who is signed in, since a person can leave their organization or move to another while ShipTok sleeps. Another person or organization behind the same key ends the sign-in, and a changed name or picture only updates what shows.
- **[STRICT]** Join existing organization (`ShipTok/Auth/JoinOrganizationView.swift`) tells the person to ask their organization's owners and admins for Revyl's invite, or has Revyl ask them: their work email goes to `POST organization-join-requests` with no key. Revyl answers the same whether or not an organization matched, and so does the confirmation, so the screen never reveals which organizations use Revyl.
- **[STRICT]** Sign out calls `DELETE revyl-sign-in/api-key`, which revokes the key and the push registrations made with it. The app goes on even if that call fails: it deletes the Keychain sign-in, stops registering for push, and stops the feed's work and waits for it (Feed Caching).
- **[STRICT]** Delete my Revyl account calls `DELETE revyl-account`: Revyl deletes the account, every comment, reply, reaction, vibe and setting it made in ShipTok, its GitHub username, and its push registrations, and the iPhone's part follows (Ownership And Boundaries). Revyl refuses an Owner of any organization with `revyl_account_owns_organization`, since deleting from a phone would strand the organization, and the app shows Revyl's own explanation. Settings and the repository picker's Account sheet offer the same account actions.
- **[STRICT]** A launch deletes the `github-sign-in` Keychain item that builds signing in with GitHub kept, along with their caches and defaults keys, and when there was one the first screen says ShipTok signs in with the person's Revyl account.

## Repositories

- **[STRICT]** `GET repositories` lists every repository the organization's active installations of Revyl's GitHub App cover, newest push first, and ShipTok adds no allowlist of its own. The person's choice is kept on the iPhone per Revyl account (defaults `feed-repository-revyl-<revyl user id>`). With no choice the picker opens, and when the list holds exactly one repository the app chooses it for them. There is no default repository.
- **[STRICT]** An empty list says the organization hasn't installed Revyl's GitHub App on any repository and links to Revyl's GitHub integration docs. A feed read refused with `repository_not_found` or `github_app_not_installed` sends the person back to the picker with Revyl's message, never to the first screen.
- **[STRICT]** Every mode, deck and saved feed belongs to one repository, and changing the choice saves the current repository's feeds before opening the chosen one's. The inbox and the push notifications span the whole organization (Inbox).

## Report And Hide

- **[STRICT]** Everything people post that ShipTok shows can be reported and its poster hidden, as App Store guideline 1.2 requires of an app that shows user-generated content (`ShipTok/Moderation/ReportableContent.swift`). A post (a pull request, a week or a feature) is GitHub's, so Report on GitHub opens GitHub's report form for it (`https://github.com/contact/report-content`, naming the author's login, with `[bot]` for a bot) and ShipTok keeps no report. A comment, reply or vibe is Revyl's, so Report has Revyl email the organization's owners and admins the content, its author and the post (`POST posts/{id}/comments/{comment id}/reports` or `POST posts/{id}/vibes/{vibe id}/reports`), and the app confirms "Thanks. Your organization's owners and admins will look at it." In the inbox a comment or reply can be reported, while a reaction or vibe can only be hidden.
- **[STRICT]** The app hides people by the identity their content carries. Hiding a post's author keeps their GitHub login, lowercased, and hides their pull requests, weeks and features; hiding the author of a comment, reply, vibe or reaction keeps their Revyl user id and hides their comments, replies, vibes and inbox items. The two are separate entries, so hiding someone's comment doesn't hide their pull requests. Hiding asks for confirmation first, and the person isn't told.
- **[STRICT]** The viewer's own posts offer neither Report nor Hide, so a post's More menu shows only while Revyl doesn't mark it as theirs (`feedback.viewer.is_developer`, true when Revyl matched the post's developer to the signed-in person). The app compares no GitHub login for this.
- **[STRICT]** Hidden people are kept only on the iPhone, per Revyl account (defaults `hidden-people-revyl-<revyl user id>`), listed in Settings with Unhide, and cleared by Delete my Revyl account. Hiding only filters what the iPhone shows: pages, the inbox, the "new" pill and a deck's count count only what shows. Revyl never learns whom a person hid, so its push notifications for a hidden teammate's feedback still arrive, and Settings says so. A new surface that shows what people post honors the hidden list and offers Report and Hide in the same change.

## iOS App

- **[STRICT]** `scripts/revyl/remote-build.sh` (`setup`, `compile`, `zip`, `upload-to-testflight`) is the only build pipeline, for local builds, Revyl's cloud builds, CI and App Store Connect; never fork a second one. `setup` requires Xcode 27.1 or newer, since the feed reads the system's reserved regions from the iOS 27.1 SDK, while the app still runs on iOS 17.
- **[STRICT]** ShipTok belongs to Revyl's Apple team, Revyl, Inc (`9MQ4RWNL3N`), and to no other: the project's `DEVELOPMENT_TEAM` and `upload-to-testflight` both name it. Its bundle id `ai.revyl.shiptok` is the app's only one; an extension or app group uses `ai.revyl.shiptok.<suffix>`.
- **[STRICT]** `upload-to-testflight` takes the team's App Store Connect API key from its environment at run time and keeps it only in a temporary file it deletes, so the key never enters the repository. It archives unsigned and lets the export sign with the team's cloud-managed distribution certificate, so never add a signing identity, a certificate or another team's key to a machine or the repository for it.
- **[STRICT]** The Xcode project uses a synchronized folder: files under `ShipTok/` join the target on their own, so never add per-file entries to `project.pbxproj`.
- **[STRICT]** The app holds only public configuration: the backend URL its build names and PostHog's project ingestion key. `ShipTok-Info.plist` sets `RevylBackendURL` from the `SHIPTOK_REVYL_BACKEND_URL` build setting, which names Revyl's production backend for Debug and Release alike; a build points at another backend only by setting `SHIPTOK_REVYL_BACKEND_URL`, which `remote-build.sh compile` takes from its environment. No secret, Revyl key or personal analytics key enters the app or git.
- **[STRICT]** The ShipTok key, Revyl's sign-in codes, signed media links and Revyl-hosted video links are credentials. Never log, render, copy or persist one outside the Keychain. Text the app shows or copies from a post loses every credential media link first (`ShipTok/Markdown/CredentialMediaLinks.swift`).
- **[STRICT]** The sign-in lives in one Keychain item (`ShipTok/Auth/ShipTokSignInKeychainStore.swift`): service `ai.revyl.shiptok`, account `revyl-sign-in`, readable after the first unlock and only on this device. A Debug build names its item `revyl-sign-in-test@<backend origin>`, so one backend's key never reaches another.
- **[STRICT]** ShipTok API requests follow no redirect, send no cookies, skip every cache and time out after 60 seconds. A followed redirect would carry the key or a sign-in code wherever it pointed, so a 3xx comes back as an unexpected answer.
- **[STRICT]** The Revyl sign-in runs in an ephemeral web authentication session. A shared session first shows iOS's "wants to use … to sign in" prompt, and on an unfolded iPhone Duo continuing from that prompt breaks the sign-in.
- **[STRICT]** Two launch arguments sign the app in without the web page (`ShipTok/Auth/LaunchArgumentSignIn.swift`): `-SHIPTOK_LAUNCH_SIGN_IN_REVYL_API_KEY` with a ShipTok key and `-SHIPTOK_LAUNCH_SIGN_IN_FEED_REPOSITORY_FULL_NAME` with the feed's repository as `owner/name`. When the key differs from the saved sign-in's, the app reads `GET revyl-account` with it, saves the sign-in to the Keychain, and makes the repository from `GET repositories` whose name matches, ignoring case, the person's choice; the same key on a relaunch keeps the saved sign-in. Only whoever launches the app (Revyl, Xcode or `devicectl`) can pass them, never a link or another app, and a launch from the Home Screen carries none (Revyl).
- **[STRICT]** `ShipTok/PrivacyInfo.xcprivacy` declares the data the app sends off the phone and its required-reason API uses, and the ShipTok section of Revyl's privacy policy (https://revyl.com/privacy/#shiptok) describes that data to people. A change that sends a new kind of data to Revyl or PostHog updates both in the same change, and one that uses another required-reason API, even on data that never leaves the phone, updates the manifest.
- **[STRICT]** The app is an iPhone app, portrait only and in dark mode. `ShipTok.entitlements` gives it push notifications (Push Notifications), and the microphone and speech recognition it asks for serve only spoken vibe feedback (Vibes).

## Product Analytics

- **[STRICT]** Capture product facts only through the typed events in `ShipTok/Analytics/`, which are the app's event contract, posted to PostHog's capture endpoint. Delivery never gates, fails or delays what the person does, and a change's `_completed` event is captured once Revyl answers, with that answer as its `outcome`.
- **[STRICT]** A signed-in person's events use `distinct_id` `revyl:<revyl user id>`. Nobody is signed in on the first screen, so one showing of it and what it leads to share `shiptok-first-screen-visit:<uuid>` and `first_screen_visit_id`, and a sign-in started there carries its `sign_in_attempt_id` to the completion the signed-in person captures. Every event carries `$process_person_profile` false and `$geoip_disable` true, so PostHog builds no profile and derives no location, plus `actor_type` `human`, `identity_provider` `revyl`, `source` `shiptok_ios`, `schema_version`, `app_version`, `app_build` and `environment`: `development` for Debug and `production` for Release.
- **[STRICT]** A watch counts only while a visible video in the foreground actually plays, uncovered by a sheet: never on mount, preload or download. It adds up only playing time and summarizes once, on leaving the video, as `shiptok_video_watch_completed` with its `end_reason` (`hidden`, `background` or `playback_failed`). A playback failure is reported only once the media renewal path is exhausted (Signed Media URLs), never for an expected first expiry, and analytics never changes playback.
- **[STRICT]** Events carry no content: no media URL or media id, title, comment, feedback text, repository name, or anything that identifies a person the viewer reports or hides. An event about a card names it with `subject_kind` (`pull_request`, `weekly_edition` or `feature`), `subject_id` and `subject_number`, and an event about a mode change names `previous_feed_mode` and `feed_mode` (`open`, `merged`, `weekly` or `features`).
- **[STRICT]** `schema_version` is 7. A new value of an existing property keeps it; adding or removing a property, or changing what one means, moves it.
- **[GUIDELINE]** Revyl's backend captures the confirmed outcomes (feedback added, push sent, developer matched, summary comment published), so the app captures intent and consumption; check both before adding an event.

## Card Layout

- **[STRICT]** Every screen follows Instagram Reels, and the feed page's layout (`ShipTok/Feed/FeedPageLayout.swift`) reads only the window's size, its safe area and the regions the system reports as covering it, never the device model or orientation. One rule holds on every window.
- **[STRICT]** Where a card at least as wide as a 9:16 video of its height fits centered between two columns of at least 84 points (wider when the system's trailing inset is), as on the unfolded iPhone Duo held tall, the card has rounded corners and runs from the safe area's top, kept between 8 and 30 points below the top of the window, to 30 points above a floating pill tab bar, with the rail in the right column. Anywhere else no tab bar shows, and the card runs from the window's top edge to its bottom edge, under the status bar and home indicator: beside a trailing system strip of at least 56 points that holds the rail, as on the folded Duo, or across the whole width.
- **[STRICT]** The tab bar holds the feed, the inbox with its unseen count, and Settings as the viewer's avatar (`ShipTok/Navigation/AppTabBar.swift`). Without it, the feed is home, and the inbox (a tray with the unseen count) and Settings (a gear) are glyphs drawn like the rail's: at the top of the trailing strip below every region the system reports there, or at the right end of the top row, the last one centered 23 points from the card's edge. The inbox and Settings replace the feed while it pauses, and without a tab bar each leads back with "‹ Feed", since nothing else does.
- **[STRICT]** Over a card that fills the window the top row sits 8 points below the safe area, and never higher than 32 points from the window's top; over an inset card it sits 32 points from the top, even where the Duo's status capsule covers the card's corner. The row holds the Open / Merged / Weekly / Features tabs, plain bold text with the selected one white. While a deck is open, a chevron back button takes their place (Pull Request Decks). Both keep to the widest stretch of the row at least 8 points clear of the inbox and Settings glyphs and of every region the system reports over it.
- **[STRICT]** The rail holds plain glyphs with their counts, stacked from the bottom like Reels: like, comments, react, then, for a video that loads, mute and playback speed, then the deck, then More whenever the card shows something someone else posted (Report And Hide). It starts below the navigation glyphs or the top row and below every region the system reports over its column, and its gaps shrink to fit what's left without its top climbing above its frame.
- **[STRICT]** The hero never loses more of itself than the card's shape forces. Media that loses at most an eighth of itself filling the card crops to fill it, as a 9:16 video does on the folded Duo; any other shape shows whole, centered within the layout's whole-media insets over a blurred copy of itself dimmed by 0.35, so there are no black bars and no edge of the media runs through the top row. A lone still or GIF also opens in the deck, where it always shows whole, and zooming tops out at 4x.
- **[STRICT]** A pull request's caption keeps to one line each: the author's login ("ghost" for a deleted account) with the viewer's own vibe badge (Vibes), the title, and "#<number> · merged <when>", or "updated <when>" led by "Draft · " on a draft, for an open one. A week's caption shows its "ShipTok weekly" chip and dates, a feature's its "ShipTok feature" chip and "shipped <when>", and both a title of up to two lines and a one-line hook. Tapping a pull request's caption opens its detail sheet, with the full title, description, stats, labels, everyone's vibe and reaction counts and Open on GitHub; tapping a week's or a feature's opens its deck.
- **[STRICT]** A pull request with no media, which only a feature's deck shows (Pull Request Decks), shows a summary where its media would be: its state, its additions, deletions and changed files, its labels, its description or "No description.", and a Details button for the detail sheet. The summary keeps to the band where a ShipTok video keeps everything a viewer must read, from 322/1920 of the card's height down to 1376/1920 or to just above the caption when that's higher, left of the rail, so nothing the app draws covers it.
- **[STRICT]** The caption sits on a blur under a black tint that reaches 0.65 at the caption's top and fades in over at most 80 points above it, never starting above 1376/1920 of a 9:16 ShipTok video laid out on the card, so the video's own captions stay sharp. Where the caption itself reaches above that line, the backdrop starts at the caption's top.
- **[STRICT]** A video's progress line sits 2 points above the home indicator on a card that fills the window, or 9 points from the bottom and 3 from the sides of an inset card, and the vibe feedback box rides the keyboard over the card, so the keyboard never lays the card out again.

## Swipe Gestures

- **[STRICT]** Swipe directions are a product decision (`ShipTok/Feed/FeedSwipeGestureMapping.swift`): up shows the next post, down the previous one, right casts good vibes and left bad vibes (Vibes). A double tap likes the card, or zooms back out when its hero is zoomed, and a tap pauses or resumes a video. Settings shows the gestures in its Gestures section.
- **[STRICT]** Holding a playing video past a tap's length plays it at 2x until the finger lifts. The hold is UIKit's long press of 0.3 seconds, since a SwiftUI long press on the video stops a single tap from pausing it, so it needs iOS 18; earlier systems keep the scrub.
- **[STRICT]** A sideways drag that starts on the strip around a video's progress line scrubs it instead of casting a vibe, and that strip reaches neither the tab bar nor the home indicator.
- **[STRICT]** A pinch zooms the hero around where the fingers met, and whatever the feed's drag had started gives way to it. While the hero is zoomed, one finger pans it instead of swiping, and the zoomed media stays within the whole-media insets, clear of the top row and the home indicator.
- **[STRICT]** A pull down from the first card past 0.18 of the page's height refreshes the feed (Feed Order).
- **[STRICT]** VoiceOver offers "Good vibes" and "Bad vibes" as actions on every element of a card, since a sideways swipe is the only visible way to cast a vibe.

## Feed Modes

- **[STRICT]** The top row's tabs are Open, Merged, Weekly and Features, with Merged as the default mode (`@AppStorage("feed-mode")`). Open and Merged show a repository's pull requests, Weekly one card per weekly edition and Features one card per shipped feature (`docs/shiptok-format.md`).
- **[STRICT]** Each tab can be turned off in Settings, and at least one stays on: the last one on can't be turned off, and Revyl refuses a save that turns every tab off (`feed_mode_tab_required`). A mode whose tab is off gives way to the first tab still on.
- **[STRICT]** The app holds one deck at a time, so opening a feature's deck closes an open week's and the other way round, and the mode behind the closed one shows its list again.

## Feed Order

- **[STRICT]** Each mode lists newest first (`ShipTok/Feed/PostFeedStore.swift`): Open by last update, Merged by merge, Weekly by week and Features by when the feature's issue closed, with the higher number first on a tie. Revyl serves a mode in pages of up to 25 posts, and a page can hold none yet name a next one.
- **[STRICT]** A post belongs in Open or Merged while it's a pull request in that state with at least one media item, and Revyl leaves out of both what Videos only hides: a pull request whose first media item isn't a video. The app follows the setting Revyl has saved, never a toggle still saving, so a saved feed served under the other setting is read again from its newest page.
- **[STRICT]** The mode on screen reads Revyl again as soon as it shows, every 10 seconds while the feed tab shows it, on each return to the foreground and on a pull from the first card. A refresh first reads the focused post again, then the newest page; a loaded card that sorts above the page's last card yet isn't on it has left the mode, since it closed, merged, lost its media or stopped leading with a video.
- **[STRICT]** Older pages load once 5 or fewer shown cards remain below the viewer, and keep loading until 10 more show, Revyl has no more, or the mode leaves the screen. An older page's cards go below every loaded card, so nothing moves under the viewer, and the `shiptok_older_posts_loaded` event records how many arrived and how many show. The page after the last card shows older posts loading, a failed load to retry, or the end of the repository's history.
- **[STRICT]** The card on screen and the next one are already rendered under the viewer's finger, so a newly found card never lands above or between them unless it's unseen and newer, and the "new" pill counts the unseen newer cards above the viewer and jumps to the first. A fresh copy of the focused card, a card that stopped belonging while on screen, and a card out of order because it changed on screen all wait until the viewer moves to another page or the mode leaves the screen, while the viewer's place stays.
- **[STRICT]** A post is dead for the viewer once every media item it holds is given up (Signed Media URLs); a post with no media isn't. A dead post leaves every mode and the open deck, after the viewer moves on, except the card the mode opened on before the viewer moved: that one goes at once and the next card they're shown takes its place. A post Revyl answers `post_not_found` for leaves at once.
- **[STRICT]** Refreshes, older pages and the reads around the focused card run only while the feed is on screen, never under the inbox or Settings, and stop whenever what's on screen changes.

## Feed Caching

- **[STRICT]** Each mode's feed is saved per Revyl account and repository under `Caches/post-feeds/` (`ShipTok/Feed/SavedPostFeeds.swift`): the mode, its next cursor, the Videos only setting it was read under and its posts as saved copies. A saved copy keeps no description and no media link, and its media items keep only their id, kind and whether each is a ShipTok video or Revyl-hosted, so nothing a saved feed holds opens a file.
- **[STRICT]** Feeds are saved when the app goes to the background, before a repository change and after older pages load. A launch opens the saved feeds at once and asks Revyl for each mode's newest page, and a file it can't decode is read again from Revyl.
- **[STRICT]** Downloaded media is saved per Revyl account under `Caches/post-media/revyl-user-<revyl user id>/`, named by a SHA-256 hash of the media item's id, which never carries a signed query string, and pruned after 30 days unused. A media id never changes its file, so swiping back or opening the deck reuses what loaded instead of a signed link that may have expired. A saved card's video plays from the iPhone when it's saved there, and otherwise waits for its post's read to bring a link.
- **[STRICT]** The feed's reads and saves for a sign-in run under `ShipTok/Feed/FeedViewerWork.swift`. Signing out and Delete my Revyl account stop it and wait for what's running before they go on, then remove that viewer's media, so nothing read for a sign-in is saved after it ends.
- **[STRICT]** A launch deletes the caches and defaults keys of builds that signed in with GitHub, which nothing reads.

## Signed Media URLs

- **[STRICT]** A media link plays or loads as is, with no credential: Revyl's backend signs every link a viewer needs. A Revyl-hosted video comes as a storage link signed for five minutes, and a GitHub upload as GitHub's own signed link; `url_expires_at` says when a signed link stops working, and only a fresh read of its post renews it.
- **[STRICT]** A focused card's media renews when its link has under 120 seconds left or is missing, and the next card the viewer will see is read again once its renewal is due, so a link never expires on screen. A card focused while on screen keeps its links unless a renewal is forced.
- **[STRICT]** A video downloads once, in one request capped at 100 MiB (104,857,600 bytes) that keeps streaming past its link's expiry; every later read, loops included, comes from memory, and a finished download is saved (Feed Caching). A media host may redirect to a file signed in its query string, which S3 refuses beside an Authorization header, so a redirect goes only to https and carries no Authorization or Cookie header.
- **[STRICT]** A signed link that failed is never requested again: its post's read renews it. Any other link is requested once more. A first failure is expected, so a load keeps its loading look while it renews, and an item is given up only once a link renewed after the failure fails too, or a read that started after the failure brings back the link that failed. Images retry on 408, 429 and 5xx.
- **[STRICT]** Text shown or copied never carries a credential media link: a Revyl-hosted video's tokened link (the `/api/v1/shiptok/videos/` route), however it's escaped or cased, or a media link signed in its query string (`ShipTok/Markdown/CredentialMediaLinks.swift`).

## Pull Request Decks

- **[STRICT]** A week's or a feature's card opens the deck of the pull requests its video covers, in the video's order, read in one `GET posts/{id}/deck` request and read again on a pull, a retry, or a return to a deck whose read was cut short. A week's or feature's deck shows over its own mode, and a deck of one post, opened from the inbox or a notification, shows over whichever mode is selected and always shows that post.
- **[STRICT]** A deck leaves out a pull request closed without merging and one whose media all failed for the viewer; a week's deck also leaves out a pull request without media, while a feature's keeps it as a summary card (Card Layout). Revyl serves at most 30.
- **[STRICT]** The deck button on a week's or a feature's card shows a count only once that deck has been read, as the posts its last read held less the hidden and dead ones, so it never counts a card the deck leaves out. On a pull request the deck button opens its media and shows when it has more than one item or its hero is a still or GIF.
- **[STRICT]** While a deck is unread the deck refreshes by reading it; once read, it reads its focused card again every 10 seconds, and a pull reads the first card again. The card under the viewer's finger keeps the copy they see until they move on, and a deck that opened on a dead card skips it at once while the viewer hasn't moved.
- **[STRICT]** The back button reads "Week of <dates>" for a week, "Features" for a feature and "Back" for a single post, and the page after the last card reads "That's the week of <dates>", "That's “<title>”" or "That's this post". Leaving a deck stops its read while the viewer's place in it stays.

## Likes And Reactions

- **[STRICT]** The reactions are thumbs_up, thumbs_down, laugh, hooray, confused, heart, rocket and eyes, and a like is heart. `PUT` and `DELETE posts/{id}/reactions/{reaction}` set them on a post and `posts/{id}/comments/{comment id}/reactions/{reaction}` on a comment.
- **[STRICT]** The like glyph's long press of 0.35 seconds opens every reaction, and the react glyph shows the viewer's non-heart reaction. A double tap likes (Swipe Gestures).
- **[STRICT]** The viewer's changes to one reaction on one post or comment reach Revyl in the order they were tapped, and only the newest one failing restores what the app shows. A reaction or vibe the viewer just set wins over reads while its write runs.

## Vibes

- **[STRICT]** A vibe is a person's good or bad verdict on a post, with optional feedback, kept by Revyl and shown to the post's developer (Inbox). `PUT posts/{id}/vibe` with `{vibe, feedback_text}` saves it, one per person per post, so a new vibe replaces their earlier one. `DELETE posts/{id}/vibes/{vibe id}` removes it, for its author or for an organization's Owner or Admin on anyone's.
- **[STRICT]** A vibe waits five seconds for Undo before it's sent, and the vibes still waiting post before the app is suspended. A vibe that fails shows a toast with Retry.
- **[STRICT]** The viewer's vibe badge on the card is how they remove it later, after "Remove your good vibes?" or "Remove your bad vibes?".
- **[STRICT]** The feedback box opens after a vibe when the person's setting asks for it, off for good vibes and on for bad ones by default (Settings). It takes typed or dictated text and never blocks the swipe.
- **[STRICT]** A sideways swipe is the only visible way to cast a vibe, so VoiceOver offers both on every element of a card (Swipe Gestures).

## Comments

- **[STRICT]** A post's comments and vibes are Revyl's (`ShipTok/Social/PostCommentsStore.swift`). `GET posts/{id}/comments` serves top-level comments oldest first, 50 a page, each with every reply under it, and `GET posts/{id}/vibes` serves the vibes oldest first. The sheet merges comments and vibes by time, heads them "N comments · M vibes", and reads its pages again every five seconds while open and on a return to the foreground.
- **[STRICT]** `POST posts/{id}/comments` with `{body, parent_comment_id}` adds a comment, or a reply when `parent_comment_id` names the comment it answers, a top-level comment or a reply. Revyl files every reply under its thread's top-level comment, since replies are one level deep, and records what it answers in `reply_to_comment_id` and `reply_to_author`; a reply that answers another reply shows "Replying to" that reply's author. `DELETE posts/{id}/comments/{comment id}` deletes a top-level comment with its replies, and a reply with every reply that answers it, directly or through another reply, for its author or an organization's Owner or Admin. The delete confirmation says which.
- **[STRICT]** A long press on a comment offers Reply, Copy, Report and Hide for someone else's, and Delete when Revyl says the viewer can delete it, beside a reaction picker; a vibe offers Copy, Report, Hide and Delete the same way (Report And Hide).
- **[STRICT]** The card's comment count is Revyl's `feedback.comment_count`, which counts comments and replies.

## Inbox

- **[STRICT]** The inbox (`ShipTok/Inbox/DeveloperInboxStore.swift`) is the feedback on the viewer's own posts, the replies that answer their comments and replies, and the replies in threads they started, newest first, as `GET inbox` serves it: likes and reactions, vibes, comments and replies, never the viewer's own. A reply reads "replied to your comment" when its `reply_to_author` is the viewer and "replied in your thread" otherwise. A post is the viewer's when Revyl matched its GitHub author to them: by the GitHub username they set in Settings, or, when no member of the organization set that account, by the author's public GitHub email or else the emails on the pull request's commits they authored. So a person whose GitHub emails differ from their Revyl email gets their posts' inbox items and notifications only once they set their GitHub username. A reaction on a comment makes no inbox item.
- **[STRICT]** Whether an item is read lives in the Revyl account, so every device and the web agree. Leaving the inbox calls `PUT inbox/read-through` with the newest item's `created_at` exactly as Revyl spelled it, to the microsecond, and Revyl answers with the unread count. The inbox reads Revyl again every 15 seconds while open, on a return to the foreground and on a pull, and people the viewer hid never reach it.
- **[STRICT]** Opening an item opens its post in a mode whose tab shows it, or as a one-post deck when none does, and opens its comments, on the item's comment when it names one, unless the item is a reaction.
- **[STRICT]** With nothing yet, the inbox says what will land there: teammates' likes, reactions, vibes and comments on the viewer's pull requests and videos, and replies to their comments.

## Push Notifications

- **[STRICT]** Revyl pushes each new piece of feedback on a person's posts, and each reply that answers their comment or reply or lands in a thread they started, to every iPhone they're signed in on, never to the person who gave it. A reaction on a comment pushes nothing. Once signed in, ShipTok asks once for permission to show alerts, sounds and badges, and while it's allowed each activation registers the device with `POST push-notification-devices` (`apns_device_token` as hex, `apns_environment` `development` for Debug or `production` for Release).
- **[STRICT]** A notification's `shiptok` payload holds `post_id`, `inbox_item_id` as `<kind>:<id>`, and `comment_id` when there is one. A tap opens the post the way an inbox item does (Inbox), comments included unless the kind is `reaction`, and captures `shiptok_push_notification_opened`. A notification that arrives while ShipTok is open shows as a banner.
- **[STRICT]** Sign out revokes the device's registrations with the key, and Delete my Revyl account deletes all of the account's (Revyl Sign-In).

## Settings

- **[STRICT]** A person's settings live in their Revyl account, so every device and the web share them: `GET` and `PUT revyl-account/settings` with `shows_good_vibes_feedback_box` (off by default), `shows_bad_vibes_feedback_box` (on), `shows_only_posts_with_videos` (on) and `shows_open_feed_mode_tab`, `shows_merged_feed_mode_tab`, `shows_weekly_feed_mode_tab` and `shows_features_feed_mode_tab` (all on).
- **[STRICT]** Saves run one at a time and each sends every setting. What shows is the saved settings with each setting's newest change still saving on top, so a read never shows an old value over a toggle and a read a save overtook is dropped. A failed save may still have landed, so the app reads the settings again and shows what Revyl has, retrying for about a minute while Revyl is unreachable.
- **[STRICT]** Settings shows the account (name, email, "Signed in to Revyl in <organization>" and GitHub username), the feed (Repository and Videos only), the feed tabs (Feed Modes), vibe feedback, the organization, hidden people (Report And Hide), the gestures, privacy and support, Sign out and Delete my Revyl account.
- **[STRICT]** The organization's one setting, "Feedback summary on GitHub", decides whether Revyl's GitHub App keeps one comment on each pull request and issue with feedback, summing up its likes, reactions, vibes and comments (`docs/shiptok-format.md`). It's on by default, `GET` and `PUT organization-settings` read and save it, and only the organization's owners and admins change it: the toggle is disabled unless Revyl says `viewer_can_change`, and Revyl refuses anyone else with `organization_admin_required`. Turning it off deletes those comments, and turning it on posts them again. A failed save may still have landed, so the app reads the setting again and shows what Revyl has, as it does for a person's settings.
- **[STRICT]** GitHub username (`ShipTok/Settings/GitHubAccountView.swift`) names the GitHub account whose pull requests are the person's own in their organization (Inbox). It's a name, never a GitHub sign-in. `GET`, `PUT` (`{"login"}`) and `DELETE revyl-account/github-account` read, set and remove it, and Revyl trims the login, drops one leading `@` and looks the account up on GitHub, so the field takes a login as typed, with no autocapitalization or autocorrection. One member of an organization can set each account, and its owners and admins can change anyone's through Revyl, so Settings reads it each time it opens; the app sets only the person's own. A refused save shows Revyl's own words (`github_login_invalid`, `github_account_not_found`, `github_account_not_a_person`, `github_account_set_by_another_person`, which names who set it, `github_app_not_installed` and `github_unavailable`). A failed change may still have landed, so the app reads it again and shows what Revyl has, as it does for a person's settings.

- **[STRICT]** Check layout on the iPhone Duo only with a build from the iOS 27.1 SDK or newer, as CI and TestFlight builds are, since the feed finds the Duo's status strip through the reserved regions that SDK reports.

## Revyl

- **[STRICT]** `.revyl/config.yaml` on `main` is the Revyl project's whole configuration: its session profiles, its `development` build profile, its pull request review with proof of changes, and the workflows it runs. Revyl reconciles it from `main`, a pull request's runs use the pull request's own copy, and Revyl rejects dashboard and `revyl config push` edits while git owns it, so change it only in git and run `revyl config validate` before committing it.
- **[STRICT]** `.revyl/tests/` holds one Revyl test per journey through the app, and runs read them from git (`run_test_definitions_from_git`), a pull request's runs at its head commit. A change to a journey updates its test in the same change, and a new journey gets a new test, added to the ShipTok journeys workflow that `.revyl/config.yaml` names. Push a new or changed test with `revyl test push` before committing it, and commit the `_meta` it writes, since `_meta.remote_id` ties the file to its test in Revyl.
- **[STRICT]** Every test, session and proof signs in as Revyl's test account in the Revyl Benchmarks organization and reads RevylAI/kyle-expo, whose pull requests are the fixtures. They sign in through the launch arguments (iOS App), from two launch variables of the organization: `SHIPTOK_LAUNCH_SIGN_IN_REVYL_API_KEY`, the test account's ShipTok key, secret and readable by automated runs, and `SHIPTOK_LAUNCH_SIGN_IN_FEED_REPOSITORY_FULL_NAME`, RevylAI/kyle-expo. Every test lists both under `env_vars`, since test runs and workflows run no session profile; Atlas runs none either and explores signed out (CI And Releases).
- **[STRICT]** `.revyl/config.yaml` makes `signed-in` the default session profile, so `revyl device start`, `revyl dev`, proof of changes and the Open preview link start ShipTok signed in on RevylAI/kyle-expo. The profile runs `scripts/revyl/signed-in-session-profile.py`, which reads both launch variables with `revyl global launch-var get --reveal` and hands them to the app, the key as a secret launch value. A raw session gets the same sign-in with `--session-profile none --launch-var SHIPTOK_LAUNCH_SIGN_IN_REVYL_API_KEY --launch-var SHIPTOK_LAUNCH_SIGN_IN_FEED_REPOSITORY_FULL_NAME`, and `--session-profile none` alone starts at the first screen.
- **[STRICT]** Every session and test shares one key, and signing out with it revokes it. When it's gone or Revyl refuses it, a member runs `scripts/revyl/save-session-sign-in.py` from the repository root with their own Revyl login or personal API key: it signs ShipTok in to Revyl as the test account the way the app does, in Google Chrome, and saves the new ShipTok key in `SHIPTOK_LAUNCH_SIGN_IN_REVYL_API_KEY`. `--backend-url` names the backend the key is for, the one the session's build points at, and nothing the script prints holds a link, code or key.
- **[STRICT]** A test or session never taps Sign out or Delete my Revyl account, never submits Join existing organization, GitHub's report form or a comment's or vibe's Report, and never changes the organization's Feedback summary on GitHub toggle. It undoes every like, reaction, comment, reply and vibe it makes before it ends, puts back every setting it changes, the GitHub username included, and touches no repository but RevylAI/kyle-expo.
- **[STRICT]** Every build CI uploads carries its repository, head commit, branch and pull request, which proof of changes and the pull request's workflows find it by; `revyl build upload` reads them from GitHub Actions, so keep uploads on it.
- **[STRICT]** `.agents/skills/`, linked for Claude Code from `.claude/skills/`, holds Revyl-managed skills from `revyl skill install`. Never edit them in place; when the Revyl CLI version pinned in `.github/actions/install-revyl-cli/action.yml` moves, refresh them with `revyl skill update` from that version.

### Revyl Verification

When developing or changing a feature in this repo, use the Revyl dev loop to verify the behavior on a device before finishing.

- Read and follow the local `revyl-cli-dev-loop` skill (`.agents/skills/revyl-cli-dev-loop/SKILL.md`) before running Revyl commands. `revyl dev --remote --build-profile development --platform ios` builds the checkout on Revyl's cloud builder and opens it on a cloud iPhone, so it needs no Mac, and the session starts signed in through the default session profile (Revyl).
- Verify the user-visible outcome with device evidence, such as `revyl device screenshot`, `revyl device report --json` or explicit interaction through `revyl device instruction`, and run the journey tests the change touches with `revyl test run <test name>`.
- Summarize Revyl verification in the final response: what path was exercised, what evidence was captured, and any issues or limitations. If Revyl can't be run, state the concrete blocker and the fallback verification used.

## CI And Releases

- **[STRICT]** `.github/workflows/ci.yml` runs on every pull request and every push to `main`: a gitleaks scan of the files and the history with `.gitleaks.toml`, then `scripts/revyl/remote-build.sh` (`setup`, `compile`, `zip`) on GitHub's `xcode-27` runner with Xcode 27.2, uploading the Debug simulator build to Revyl. On `main` it also runs the workflows `.revyl/config.yaml` names on that exact build, and explores the build with Atlas, one exploration at a time with every build queued, signed out from the first screen, never completing a Revyl sign-in or submitting Join existing organization. A fork's pull request gets no secrets, so it builds without uploading.
- **[STRICT]** `main` works against Revyl's production backend at every commit, and its journeys run on a build that uses production, so they show whether it does. An app change that needs new backend behavior waits on its own pushed branch, named after the cognisim-monorepo pull request it ships with as `cognisim-<number>-<what it does>`, and merges to `main` only once that behavior is live in production. The app relies only on what production serves.
- **[STRICT]** `.revyl/config.yaml` is the only place that names the Revyl app and workflows: CI reads them with `revyl config show --json`, and the repository's GitHub settings hold only secrets.
- **[STRICT]** `.github/workflows/release.yml`, run by hand with a build number higher than every build already uploaded for the version, is the only way builds reach App Store Connect: it runs `upload-to-testflight` with the App Store Connect API key in the repository secrets `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_API_ISSUER_ID` and `APP_STORE_CONNECT_API_PRIVATE_KEY`.
- **[STRICT]** This repository is public, and so are its Actions logs: no workflow prints a secret, a key, an internal hostname or customer data.
- **[STRICT]** Workflows pin every action to a commit and the Revyl CLI and gitleaks to a release version.
