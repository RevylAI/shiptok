# ShipTok Guide For AI Contributors

This repository is ShipTok, Revyl's iOS app (SwiftUI, iOS 17+). People sign in with Revyl using their GitHub account, and that sign-in and each person's settings run on Revyl's backend, under its ShipTok API (`/api/v1/shiptok/`), which lives outside this repository. ShipTok is a vertical feed of the merged pull requests that carry media in the repository the person chooses, one pull request per swipe, its ShipTok video or other media first, and in weekly mode one video per week. Likes, reactions, comments and vibes are GitHub reactions and comments written as the signed-in person, so GitHub is the record.

---

# Guidance & Rules

The rules below are binding for the whole repository.

## Ownership And Boundaries

- **[STRICT]** The app reads and writes GitHub directly with the signed-in person's GitHub token; only the demo reads through Revyl's backend (Demo Mode). Revyl's hosted media endpoints serve uploaded videos and posters without that token; playback follows their redirects without forwarding GitHub authorization. The app reads no Revyl product database directly.
- **[STRICT]** GitHub is the record for pull requests, weekly videos, media, comments, reactions and vibes. The viewer's changes to one reaction on one pull request, week or comment reach GitHub in the order they were tapped, and only the newest one failing undoes what the app shows. Revyl's backend holds only what GitHub can't: it redeems and refreshes the GitHub sign-in with Revyl's GitHub App, since both need the App's client secret, and keeps each person's settings keyed by their numeric GitHub user ID, which it reads from the GitHub token on every settings request. It stores no GitHub token and never proxies a GitHub write or a person's read; its one GitHub read for the app is the demo feed (Demo Mode). Its ShipTok tables link to no Revyl user or organization.
- **[STRICT]** Sign in with Revyl is the app's only sign-in, and the app keeps no other provider's session or a reader for one. Its identity is the person's GitHub account through Revyl's GitHub App, so it needs no Revyl account or seat.
- **[STRICT]** Delete my ShipTok data removes everything ShipTok keeps for the person: Revyl's backend deletes their settings and revokes the GitHub token the app presents, and the app then deletes its Keychain sign-in, caches and defaults and signs out. Neither it nor Sign out signs out or reports success while the Keychain still holds the sign-in, and Delete my ShipTok data reports success only once the caches and defaults are gone too. Once Revyl's part is done the app records that in its defaults, by GitHub user ID, until the iPhone's part finishes, so trying again, the next launch or the next sign-in, before it opens GitHub, finishes only the iPhone's part, and a launch never restores the revoked sign-in: it stays on the sign-in screen saying why while the iPhone's part still fails. It revokes only that token, never the person's whole authorization of the GitHub App, which would also sign them out of every other Revyl surface on the same App. Comments, reactions and vibes are GitHub's record and stay there. Anything new the backend or app keeps per person joins this deletion in the same change.
- **[STRICT]** The ShipTok format is a contract shared with Revyl's pull request review config and the people who post ShipTok videos: which pull requests are in the feed, the ShipTok video marker and tag, which media shows first, the vibe comment, and the weekly edition issue. It is documented in `docs/shiptok-format.md`. Change the parser or the vibe comment only together with that contract, and read the hidden `<!-- shiptok:... -->` markers from the raw markdown body, since GitHub's rendered HTML drops them.
- **[STRICT]** Only top-level conversation comments by people, on a pull request or a week's issue, show as comments. Bot comments, inline code-review comments and comments carrying a ShipTok tag never do, whether or not they hold a video, while media from any top-level comment, a bot's included, counts.
- **[STRICT]** A ShipTok video is a video in a description or top-level comment tagged with case-insensitive `#shiptok` or `<!-- shiptok:video -->`. Attributes in the hidden marker are ignored; authorship and hosting provider never change the tag's meaning. The newest tagged video plays first, ahead of other media. People make videos with their own tools; the app does not require or infer Revyl generation.

## Demo Mode

- **[STRICT]** Look around first, on the signed-out screen, opens a read-only demo of one public repository, so anyone, App Review included, can try the app without an account. Revyl's backend serves it from `GET /api/v1/shiptok/demo-feed` with one backend-owned GraphQL query of the repository `SHIPTOK_DEMO_REPOSITORY_FULL_NAME` names, per environment, read with the token of Revyl's GitHub App installation on that repository's owner, held about a minute per process and behind the backend's rate limiter. It never relays a client's query, reads another repository or searches, since an installation token's search covers only installed repositories. It fails closed with a 503 when the repository is unset, missing or private or GitHub refuses, and the app then stays on the sign-in screen saying why.
- **[STRICT]** The demo holds the repository's 50 most recently updated merged pull requests and 25 newest closed `shiptok-weekly` issues, each with its comments, and the app applies Feed Order and Weekly Mode to that snapshot, so a demo pull request that should stay past the 14-day window carries the `shiptok` label.
- **[STRICT]** Everything that posts to GitHub as the person (likes, reactions, comments, vibes and their spoken feedback) and everything that needs a GitHub account (Report and the inbox) asks a demo visitor to sign in instead. Signing in from the demo lands in the signed-in app. Hide works for the rest of the visit, Settings says it's a demo and offers Sign in, and nothing of the visit is saved but media files. A new write surface asks a demo visitor to sign in in the same change.

## Report And Hide

- **[STRICT]** Everything people post that ShipTok shows can be reported and its poster hidden, as App Store guideline 1.2 requires of an app that shows user-generated content. Report opens GitHub's own report form for that pull request, week's issue or comment, since GitHub hosts the content and acts on reports; ShipTok sends and keeps no report of its own. GitHub's form takes no reaction, so someone shown only for a reaction can be hidden but not reported. Hide takes everything the person wrote or posted (their pull requests, weeks, comments, vibes and media) out of the feed, decks, comment sheets, detail sheet and inbox for the signed-in person. It filters what is shown, never what is saved or fetched, so Unhide brings everything back at once.
- **[STRICT]** Hidden people are kept by GitHub login, only on the device and per signed-in person, and only in memory for a demo visit. Settings lists them with Unhide, and deleting ShipTok data clears them. A new surface that shows what people post honors the hidden list and offers Report and Hide in the same change.

## iOS App

- **[STRICT]** `scripts/revyl/remote-build.sh` (`setup` / `compile` / `zip` / `upload-to-testflight`) is the only build pipeline; never fork a second one.
- **[STRICT]** ShipTok belongs to Revyl's Apple team, Revyl, Inc (`9MQ4RWNL3N`), and to no other: the project's `DEVELOPMENT_TEAM` and `upload-to-testflight` both name it. Its bundle id `ai.revyl.shiptok` is the app's only one; extensions and app groups use `ai.revyl.shiptok.<suffix>`.
- **[STRICT]** `upload-to-testflight` takes the team's App Store Connect API key from its environment at run time and keeps it only in a temporary file it deletes; the key itself never enters the repository. It archives unsigned and lets the export sign with Revyl's cloud-managed distribution certificate, so never add a signing identity, certificate or another team's key to a machine or the repository for it.
- **[STRICT]** The Xcode project uses a synchronized folder: files under `ShipTok/` join the target automatically, so do not add per-file entries to `project.pbxproj`.
- **[STRICT]** The app holds only public configuration: the Revyl backend URL its build names and PostHog's project ingestion key. Every build uses Revyl's production backend unless the `SHIPTOK_REVYL_BACKEND_URL` build setting names another, for example a development backend with its own GitHub App. The GitHub App client secret, PostHog personal keys and database credentials never enter the app or git.
- **[STRICT]** GitHub access and refresh tokens, signed media URLs and tokened Revyl media URLs are credentials. Never log, render, copy or persist them outside the Keychain.
- **[STRICT]** GitHub sign-in runs in an ephemeral browser session. A shared session first shows iOS's "wants to use … to sign in" prompt, and on an unfolded iPhone Duo continuing from that prompt tears the GitHub sheet down before it appears, so sign-in silently does nothing there.
- **[STRICT]** A sign-in lasts until GitHub refuses to refresh it. A GitHub App user access token expires after eight hours and its refresh token works once, so the app refreshes ahead of expiry, and once when GitHub or Revyl refuses a token another refresh may have retired, one refresh at a time, saving the rotated pair to the Keychain before anyone uses it. A pair the Keychain fails to save stays in memory and is saved again before use, never refreshed anew, since its refresh token is the only one GitHub still honors. An App that doesn't expire its tokens keeps one until GitHub rejects it. A refusal ends only the sign-in whose request it answered, never a later one, and nobody can sign out while Delete my ShipTok data runs.
- **[STRICT]** `ShipTok/PrivacyInfo.xcprivacy` declares the data the app sends off the phone and its required-reason API uses, and the ShipTok section of Revyl's privacy policy (https://revyl.com/privacy/#shiptok) describes that data to people. A change that sends a new kind of data to Revyl, PostHog or GitHub updates both in the same change, and one that uses another required-reason API, even on data that never leaves the phone, updates the manifest.
- **[STRICT]** Test phones that sign in use a build pointed at a development backend. GitHub keeps at most ten tokens per person for one app and revokes one of them for each sign-in past that, so every sign-in through Revyl's production GitHub App spends one of that person's ten.
- **[STRICT]** The feed's repository is the person's choice among every repository their sign-in reaches, meaning where an organization installed the build's GitHub App and the person has access, with no other allowlist; Debug and Release share one picker. The choice is remembered per person, and with none the app opens RevylAI/shiptok-demo, the demo's public repository, when it's reachable, else the picker. A repository the App stops reaching sends the person back to the picker, not to sign-in. Each API client keeps its repository fixed, and changing the choice rebuilds the feed, weekly and inbox state; saved feeds and inbox read positions are scoped by repository and person.

## Product Analytics

- **[STRICT]** Capture native product facts through the typed boundary in `ShipTok/Analytics/`, whose typed events are the event contract. Keep delivery independent of product success, and record GitHub write success only after GitHub confirms it.
- **[STRICT]** Use the numeric GitHub user ID saved with the sign-in for analytics identity. Until GitHub names the person, a sign-in attempt's events use the attempt's own ID, which its completion carries. A demo visit's events use the visit's own ID, which a sign-in started from it carries. A login is renameable, and a repository owner is not a Revyl person or organization mapping. Events never let PostHog derive a location. Debug and Release use the web app's PostHog project, separated by `environment=development` and `environment=production` respectively.
- **[STRICT]** A watch starts only while a visible, foreground video is actually playing, never on mount, preload or download. Accumulate only playing time, exclude pauses, buffering, scrubbing and comment-sheet occlusion, and summarize on leaving the video instead of emitting frame or loop events. Analytics visibility must not change playback behavior. Report terminal playback failures only after the existing media-renewal path is exhausted, not an expected first URL expiry. Do not send media URLs or media IDs, tokens, titles, comments, feedback text or other content. Subject and source-comment IDs are correlation keys, not breakdown dimensions. No repository name, and nothing that identifies a person the viewer reports or hides, enters analytics.

## Card Layout

- **[STRICT]** Every screen follows Instagram Reels on the unfolded iPhone Duo held taller than wide, and other windows keep the same look. A feed page is a media card with small rounded corners, running from at most 30 points below the top of the screen to 30 points above a floating pill tab bar. The card is centered between two 84-point columns (wider when the system's trailing strip is) with the action rail in the right column whenever that leaves the card at least as wide as a 9:16 video of its height, so the leading column never narrows a Reels video; otherwise a trailing system strip of at least 56 points holds the rail beside the card, as on the folded Duo; otherwise the card spans the window with 8-point margins and the rail sits over its trailing edge, as on other iPhones. The rail starts below every region the system reports as covering its column, such as the Duo's status strip with an expanded island or Live Activity, and its gaps shrink to fit what's left, down to overlapping the padding around its glyphs. Placement reads only the window's size, its safe area and those reported regions, never the device model or orientation.
- **[STRICT]** The rail holds plain glyphs with their counts: like (a long press opens every reaction), comments, react, vibes (good, bad, and removing your own), mute and playback speed for a video that loads, and the deck: on a pull request when there is more than one item or the hero is a still or GIF, and always on a week, where it opens the week's pull requests; and last, More, whenever the card shows something someone else posted (Report And Hide). The speed, also among the deck's controls, cycles 1x, 1.5x and 2x for every video and is remembered on the device. The PRs / Weekly switch sits over the card's top left, inside the format's top safe zone, and becomes the way back while a week's pull requests are open. The caption sits over the card's lower left above a thin video progress line. The tab bar holds the feed, the inbox and settings; the inbox and settings replace the feed while its video is paused.
- **[STRICT]** The hero never loses more of itself than the card's shape forces. A shape that loses at most an eighth of itself when filling the card crops to fill it, as a 9:16 video does on other iPhones and the unfolded Duo held tall. Any other shape, a wide screenshot or GIF on a tall card included, shows whole, centered over a blurred copy of itself, so there are never black bars and no part of a screenshot is cut off.
- **[STRICT]** Text on a card stays short: the author, the viewer's own vibe badge, a title of at most two lines, and the number and merge time; a week shows its "ShipTok weekly" chip, dates, title and hook instead of the author, number and merge time. Everything else (the description, stats, labels, everyone's vibe and reaction counts) is one tap away in the detail sheet, and the swipe legend lives in Settings.

## Feed Order

- **[STRICT]** The feed holds the pull requests with media merged in the last 14 days, plus every pull request labeled `shiptok` whose hero is a ShipTok video, whatever its age, so tagged examples never age out. Nothing older is ever searched: a refresh searches the window, and before it only pull requests labeled `shiptok`. A card from before the window whose label is removed drops out of both searches, so after them each refresh also reads again by number the feed's card from before the window read or tried longest ago, once five minutes have passed, and that card leaves once it no longer belongs or GitHub no longer has it. The feed is ordered by its hero's group, then newest merge first. The groups are tagged ShipTok videos, then other videos, then images and GIFs. A label alone does not tag the media.
- **[STRICT]** A launch with nothing saved reads the labeled pull requests in one search and opens on them, so the first card shows within seconds, then reads the window in parallel merge-date ranges. A pull request found after the feed opened sorts only into the cards after the one in focus and the one after it, since both are already rendered, so nothing moves under the viewer. A newly merged pull request takes its sorted slot anywhere in the feed, and when that slot is above the viewer the "new" pill counts it and jumps to the first such card.
- **[STRICT]** A pull request none of whose media loads, even from a renewed URL, leaves the feed while the viewer is still above it, so the feed never shows a dead card ahead of the viewer. On a card the viewer has already reached, and on a deck page, media given up says its video or image is unavailable; until then it keeps the loading look.

## Feed Caching

- **[STRICT]** Nothing already loaded is fetched again. The feed is saved on the device for the repository and signed-in GitHub login (a demo visit's is not), with the moment every update before it was applied, and a launch opens on it at once and then searches only the pull requests updated since; a saved feed older than the window is read again from scratch. Media files are saved under a hash of their media item's id and play from the device on later launches. The feed, weeks, decks and the demo share those files, so a file goes only once it has gone 30 days without being saved or shown, never by one surface's list. Comments, reactions and vibes stay live: the card in focus is refetched as before.
- **[STRICT]** A saved feed holds no signed media URL, tokened Revyl media URL, raw description or comment body, or rendered HTML. A saved card's media item keeps its URL only when it isn't a credential, so its media plays from the device or waits for the refetch of the card in focus. A tokened Revyl media item's id is a hash of its canonical URL, never the token or the redirect target.

## Weekly Mode

- **[STRICT]** The feed has two modes, per pull request (the default) and weekly, switched at the card's top left and remembered on the device. Weekly mode shows one card per published week, newest week first, playing its video. Each mode, and a week whose pull requests are open, keeps its own place.
- **[STRICT]** A week is a closed issue in the chosen repository labeled `shiptok-weekly` whose description follows the weekly format in the ShipTok format. Its media can be untagged: tags only prioritize the newest tagged video, never exclude other media. The app lists weeks through the issues API, never search, so a week shows the moment it closes; it skips an open issue, a pull request, a description outside the format or a week with no media, and never edits, reopens or closes a week. Posting weeks is the poster's job, never the app's.
- **[STRICT]** A week takes likes, reactions, comments and vibes on its issue exactly as a pull request does. Its deck opens the week's pull requests as ordinary pull request cards in the video's order, read by number since a week can reach past the feed's window, each with its own likes, reactions, comments and vibes.

## Signed Media URLs

- **[STRICT]** GitHub upload URLs come from its rendered HTML, signed for the reader, and stop working a few minutes after the fetch. A Revyl-hosted video's canonical source is the video target in the raw description or comment, including when a poster links to it; the poster is not another deck item. A media item's identity never includes the URL's query string, a video downloads once in a single request, never past the size limit in `docs/shiptok-format.md`, and every replay, loops included, plays from memory, and a fresh URL is fetched only after a load fails: a URL signed in its query string is renewed by refetching the pull request, and an unsigned one, such as a hosted video's tokened link that redirects to the file, by requesting it once more. A failed item is given up only once its renewed URL fails too, or a read that started after the failure brings back the URL that failed, and a failure no such read has settled yet waits for the next one, so a renewal that fails offline is settled once the app reads again. Video redirects carry no GitHub authorization, and never replace the canonical cache identity.

## Vibes

- **[STRICT]** A person has one vibe per pull request or week: a new vibe comment replaces their earlier vibe comments on it, and undoing it, from the toast or later from their own vibe badge or the rail's vibes button, deletes it.
- **[STRICT]** The vibe feedback box never blocks the swipe. The feed advances at once, the box is a per-person setting (on for bad vibes and off for good vibes by default), and feedback typed or spoken before the next swipe posts with its vibe.

## Swipe Gestures

- **[STRICT]** Swipe directions are a product decision: up shows the next card, down the previous one, right casts good vibes, left casts bad vibes, and a double-tap likes. A single tap on a playing video pauses it, showing a play glyph, and another tap resumes it; it waits out a double-tap, so a like never pauses, and the rail and caption keep their own taps. Change them only in the feed's swipe gesture mapping (`FeedSwipeGestureMapping`); the card stamp, settings, deck and the rail's vibes button read that mapping. Swapping directions within an axis is safe, while moving navigation to the horizontal axis needs deck layout changes.
- **[STRICT]** Holding a playing video past a tap's length plays it at 2x, with a "2x" hint, until the finger lifts and it returns to the chosen speed, and a sideways drag that starts on the strip around a hero's progress line, or on a deck page's line, scrubs it with a time readout, so neither costs a tap, double-tap, swipe or vibe, and neither reaches the tab bar or home indicator. The hold is UIKit's long press, since a SwiftUI long press on the video stops a single tap from pausing it, so it needs iOS 18; earlier systems keep the scrub.

## Validation

- **[STRICT]** Before completing an app change, run the remote build (`setup`, `compile`, `zip`) on a macOS runner with Xcode 27.1 or newer and fix every warning the change introduces.
- **[STRICT]** Check layout on the iPhone Duo only with a build from the iOS 27.1 SDK or newer, as TestFlight builds are: an app built with an older SDK is kept out of the Duo's status strip, so it lays out in a smaller window than the one people get.

## Revyl

- **[STRICT]** `.revyl/config.yaml` on `main` is the Revyl project's configuration. Revyl's GitHub App applies it on every push to `main` and refuses dashboard and `revyl config push` edits, so change it only in git and run `revyl config validate` before committing it.
- **[STRICT]** `.revyl/tests/` holds one Revyl test per journey through the app and `.revyl/modules/` the steps they share, and runs read them from git (`run_test_definitions_from_git`), a pull request's runs at its head commit. A change to a journey updates its test in the same change, and a new journey gets a new test, added to the ShipTok journeys workflow that `.revyl/config.yaml` names. Push a new or changed test or module with `revyl test push --include-modules-and-scripts` before committing it, and commit the `_meta` it writes, since `_meta.remote_id` ties the file to its test in Revyl.
- **[STRICT]** The journeys run signed out, through Look around first, and never sign in to GitHub.
- **[STRICT]** Every build CI uploads carries its repository, head commit, branch and pull request, which Revyl's proof of changes and pull request workflows find it by; `revyl build upload` reads them from GitHub Actions, so keep uploads on it.
- **[STRICT]** `.agents/skills/`, linked for Claude Code from `.claude/skills/`, holds Revyl-managed skills from `revyl skill install`. Never edit them in place; when the Revyl CLI version pinned in `.github/actions/install-revyl-cli/action.yml` moves, refresh them with `revyl skill update` from that version.

### Revyl Verification

When developing or changing a feature in this repo, use the Revyl dev loop to verify the behavior on a device before finishing.

- Read and follow the local `revyl-cli-dev-loop` skill (`.agents/skills/revyl-cli-dev-loop/SKILL.md`) before running Revyl commands. `revyl dev --remote --profile development --platform ios` builds the checkout on Revyl's cloud builder and opens it on a cloud iPhone, so it needs no Mac.
- Verify the user-visible outcome with device evidence, such as `revyl device screenshot`, `revyl device report --json`, or explicit interaction through `revyl device instruction`, and run the journey tests the change touches with `revyl test run <test name>`.
- Summarize Revyl verification in the final response: what path was exercised, what evidence was captured, and any issues or limitations. If Revyl cannot be run, state the concrete blocker and the fallback verification used.

## CI And Releases

- **[STRICT]** `.github/workflows/ci.yml` runs on every pull request and push to `main`: a gitleaks scan with `.gitleaks.toml`, then `scripts/revyl/remote-build.sh` (`setup`, `compile`, `zip`) on GitHub's `xcode-27` runner with Xcode 27.2, uploading the build to Revyl. On `main` it runs the ShipTok journeys workflow on that exact build and explores it with Atlas, one exploration at a time with every build queued. Fork pull requests get no secrets, so they build without uploading.
- **[STRICT]** `.revyl/config.yaml` is the only place that names the Revyl app and workflows: CI reads them from it with `revyl config show --json`, and the repository's GitHub settings hold only secrets.
- **[STRICT]** `.github/workflows/release.yml`, run by hand with a build number, is the only way builds reach App Store Connect: it runs `upload-to-testflight` with the App Store Connect API key in the repository secrets `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_API_ISSUER_ID` and `APP_STORE_CONNECT_API_PRIVATE_KEY`.
- **[STRICT]** This repository is public, and so are its Actions logs: no workflow prints a secret, token, internal hostname or customer data.
- **[STRICT]** Workflows pin every action to a commit and the Revyl CLI and gitleaks to a release version.
